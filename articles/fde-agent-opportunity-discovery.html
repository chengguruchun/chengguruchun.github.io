FDE · Agent Discovery · 2026-09-17

FDE 的新价值：识别业务复杂度，而不是简单交付 Agent

在 Agent 时代，FDE（Forward Deployed Engineer）的价值不只是把产品部署到客户，而是把真实业务中的复杂度识别出来，拆解成 Decision Units，并判断哪些复杂度值得被 Agent 化。

1. FDE 真正面对的问题

客户可能说：“我要解决排产问题。”但 FDE 不能直接把“排产”做成一个 Agent，而应该继续追问：到底什么叫排产问题？为什么要重新排？谁在决定？依据什么？有哪些约束？异常有哪些？多久发生一次？错误的代价是什么？最后如何知道成功？

最后可能发现，客户以为需要的是“排产 Agent”，真正高价值的却是“异常恢复 Agent”。

FDE 的价值，是把模糊的业务问题重新建模成可执行、可验证的决策问题。

2. 从 Business Process 到 Decision Unit

Business Reality
       ↓
       FDE
       ↓
Complexity Map
       ↓
Decision Units
       ↓
Agent Opportunity Map
       ↓
Runtime Design

不要只按部门或岗位拆系统，而要把一个岗位继续拆成具体决策单元。例如生产管理可以拆成排产、插单、产能分配、工厂选择、物料调度、异常恢复、交期调整。

3. 如何识别业务复杂度

我会重点看六个维度：

  • 随机性：环境是不是经常变化？
  • 组合复杂度：有多少资源、约束和方案需要组合？
  • 决策频率：这个决策多久发生一次？
  • 反馈速度：结果多久可以知道？
  • 可验证性：能不能客观判断成功或失败？
  • 错误成本：Agent 做错一次有多严重？

因此，Agent 化并不是“随机性越高越好”，而更像是：

高随机性
+
高组合复杂度
+
高决策频率
+
快速反馈
+
高可验证性

→ Agent Opportunity

4. 不同复杂度，对应不同技术形态

场景特征形态
数据同步、状态更新低复杂度、规则明确Automation
固定审批、固定工艺确定性强Workflow
排产、调度、供应商匹配高组合 + 动态变化 + 可验证Agent
重大质量、安全、重大采购高复杂度 + 高错误成本Agent + Human

因此 FDE 的工作不是见到业务就“上 Agent”，而是识别业务复杂度后做技术形态判断。

5. 为什么组合复杂度特别重要

制造中的一个订单可能同时涉及供应商、产线、材料、时间、物流、质量和成本。每增加一个维度，可能方案都会快速增加。

订单
× 供应商
× 产线
× 材料
× 时间
× 物流
× 质量
× 成本

传统系统往往不断增加 Rule 1、Rule 2、Rule N。但当组合空间持续扩大时，规则系统的维护成本会越来越高。Agent 的价值则可能变成在巨大可能性空间中生成、比较和调整候选方案。

6. 不要替代岗位，要替代决策单元

一个岗位通常同时包含 Routine、Decision、Communication、Judgement 和 Responsibility。Agent 最先适合接管的通常是其中可结构化、可验证的 Routine + Decision，而责任和高风险授权仍然需要治理机制。

所以不要简单设计：

Supplier Manager Agent
Production Manager Agent
Warehouse Manager Agent

而应该拆成：

Supplier Manager
├── 找供应商
├── 比较供应商
├── 判断交期
├── 监控质量
├── 处理异常
└── 调整订单

        ↓

Supplier Discovery Agent
Supplier Matching Agent
Supplier Monitoring Agent
Supplier Recovery Agent
不是替代一个职位，而是拆解一个职位中的决策单元。

       Workflow          Agent

                           │

这意味着 FDE 不是 Agent Runtime 的外围实施角色，而可能是 Runtime 的业务入口：负责发现值得被运行时接管的决策单元，并帮助建立验证闭环。

8. 从交付工程师到复杂度发现者

传统实施可以理解为：

客户业务
 ↓

 ↓

 ↓
上线

Agent 时代的 FDE 更像：

真实业务
 ↓
业务流程拆解
 ↓

 ↓
复杂度分析
 ↓
Agent Suitability
 ↓

 ↓

所以 FDE 的核心工作从“把产品部署到客户”逐渐向“理解客户业务并重新定义产品与 Agent 的边界”移动。

9. 一个可能的未来：Agent Discovery Agent

随着企业数据越来越完整，这个过程本身也可能被部分 Agent 化。系统可以分析 SOP、工单、ERP/MES 数据、操作日志、异常记录和人工决策轨迹，自动发现高复杂度、高频率、高随机性的决策单元。

Enterprise Data
      ↓
Agent Discovery
      ↓
Complexity Map
      ↓
Agent Opportunity Map
      ↓
FDE Validation
      ↓
Agent Runtime

但 FDE 仍然重要，因为真实业务中的隐性约束、责任边界和组织规则，往往不能只从日志中得到。

10. 我的暂时结论

如果把 Agent 时代的 FDE 重新定义，我会这样描述：

FDE 的核心价值不是把产品部署到客户，而是识别客户业务中的复杂决策单元，并把其中适合 Agent 化的部分转化成可验证、可运行的 Agent Runtime。

这也把几个看似不同的问题连起来了：

Business Complexity
        ↓
Decision Unit
        ↓
Agent Suitability
        ↓
Agent Architecture
        ↓
Agent Runtime
        ↓
Outcome Feedback

所以未来判断一个企业是否适合 Agent 化，可能首先不是问“有没有 LLM”，也不是问“哪个岗位会被替代”，而是问：

哪些业务决策已经复杂到传统 Workflow 不再经济，同时又具备 Agent 所需要的反馈与验证条件？

开放问题

  • 能否建立一套可量化的 Business Complexity Map？
  • Decision Unit 的边界应该由 FDE、产品经理还是 Agent Discovery 系统共同定义？
  • 如何判断一个复杂决策已经超过 Workflow 的经济边界？
  • 哪些企业数据最能暴露隐藏的决策复杂度？
  • FDE 是否会逐渐成为 Agent Runtime 的“业务编译器”，把现实业务编译成 Agent 可执行的决策空间？
