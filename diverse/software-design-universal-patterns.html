软件工程的隐形语法：从“加一层”到“广进严出”

很多设计模式看起来五花八门，但反复出现的动作其实很少：隔离、拆分、过滤、缓存、复制、延迟、反馈、收敛。也许软件工程存在一套比设计模式更底层的“隐形语法”。

思路 2026-09-23作者 chengguruchunSoftware DesignArchitectureComplex SystemsDesign Patterns

我最近连续想到两个软件工程里的“万能句式”。一个是：“没有什么是加一层不能解决的，如果有，就加两层。”另一个是：“广进严出。”前者强调间接层、抽象与解耦，后者强调粗到精、多级过滤与逐级收敛。把它们放在一起看，我越来越觉得，软件工程里大量看似不同的模式，本质上都在做同一件事：把一个难以直接处理的问题，转换成一组更容易控制的问题。

于是我想把这些反复出现的“工程直觉”尽可能放在一张地图里。它不追求覆盖所有设计模式，而是寻找设计模式背后的共同动作。

一、第一性原理：软件设计其实是在“改变问题的形状”

面对一个复杂问题，工程师通常不会直接硬解，而会先问：

  • 能不能隔离它？
  • 能不能拆开它？
  • 能不能把昂贵决策推迟？
  • 能不能提前计算？
  • 能不能先粗筛，再精算？
  • 能不能把失败限制在局部？
  • 能不能把结果留下来复用？
  • 能不能让系统根据反馈继续调整？

这些问题对应的就是一整套软件设计思想。

原问题
  ↓
抽象 / 拆分 / 隔离 / 过滤 / 延迟 / 缓存 / 复制
  ↓
更小、更局部、更可预测的问题
  ↓
组合
  ↓
系统

所以很多“架构技巧”其实不是直接解决业务问题，而是在重写问题的边界、成本、时序和可见性。

二、第一大类：增加间接层——不要让两个东西直接耦合

最经典的就是：

Any problem in computer science can be solved by another level of indirection.

它的核心不是“多加一层”，而是：让变化的一方不要直接碰稳定的一方。

思想增加的东西解决什么
抽象Interface / API实现变化
适配Adapter / Wrapper接口不兼容
代理Proxy访问控制、增强、远程化
门面Facade隐藏子系统复杂度
网关Gateway统一入口、路由、鉴权
中间件Middleware抽离横切逻辑
Sidecar旁路进程把治理能力与业务解耦
Service Mesh通信层把服务治理下沉
Anti-Corruption Layer防腐层隔离外部领域模型

甚至 DNS、虚拟内存、文件系统、容器、对象存储的抽象，都可以从这个角度理解：把真实世界的复杂变化藏在一个更稳定的间接层后面。

但这条规律也有反面：间接层不是免费的。它会增加延迟、认知负担和故障定位成本。于是才有另一句工程经验：抽象的价值来自隐藏真正变化，而不是为了抽象而抽象。

三、第二大类：分而治之——把一个复杂问题拆成多个局部问题

如果“加一层”是在增加边界，那么“分而治之”是在增加边界的数量。

复杂问题
   ↓
┌────┬────┬────┐
A    B    C    D
└────┴────┴────┘
   ↓
组合结果

它出现在几乎所有尺度：

  • 模块化、包、类、函数：拆软件。
  • 微服务：拆服务边界。
  • 分片：拆数据。
  • MapReduce：拆计算。
  • Actor：拆并发状态。
  • 多 Agent：拆决策主体。
  • 领域驱动设计：按业务边界拆模型。
  • 团队与组织：按职责拆决策。

“拆”真正解决的不是代码长度，而是局部复杂度。如果一个系统的每个局部都足够简单，人类才可能理解它，机器也才更容易自动化它。

四、第三大类：关注点分离——让一个东西不要同时承担太多维度

单一职责、AOP、MVC、Hexagonal Architecture、Clean Architecture、Control Plane / Data Plane，本质都和这个思想有关。

业务逻辑
  │
  ├── 数据访问
  ├── 权限
  ├── 日志
  ├── 事务
  ├── 网络
  └── 监控

工程师不断尝试把这些维度拆开，使一个模块的变化原因尽可能少。

这也解释了为什么“控制面 / 数据面”如此常见：决策与执行是两种不同的变化速度。控制面负责“应该怎么做”，数据面负责“现在怎么执行”。Kubernetes、Service Mesh，以及 Agent Runtime 都可以用这个坐标理解。

五、第四大类：广进严出——粗到精、逐级收敛

这是我最近觉得特别值得抽象出来的一类。

全量输入
   ↓
粗筛
   ↓
候选集
   ↓
精排
   ↓
少量候选
   ↓
重排 / 验证
   ↓
最终结果

搜索推荐里的“召回 → 粗排 → 精排 → 重排”是最直观的例子，但远不止如此：

领域粗到精
搜索召回 → 粗排 → 精排 → 重排
RAG查询理解 → 多路召回 → Rerank → 生成
计算机视觉候选区域 → 分类 → 精细定位
算法搜索Branch → Bound → Prune
编译器词法 → 语法 → 语义 → 优化 → 代码生成
数据仓库原始数据 → 清洗 → 明细 → 聚合 → 应用
安全粗粒度拦截 → 身份验证 → 权限 → 风险检查

这里有一个非常重要的工程规律：

越靠前，追求低成本、高召回；越靠后，追求高成本、高精度。

也就是：把昂贵的判断留给更小的候选集。

六、第五大类：缓存与预计算——把未来的问题提前解决

缓存的本质不是 Redis，而是：

如果某个结果未来大概率还会被需要，就不要每次重新计算。

因此缓存、CDN、物化视图、索引、预计算、编译产物、模型 KV Cache，甚至记忆系统，都可以放到同一类。

没有缓存：
请求 → 计算 → 结果
请求 → 计算 → 结果
请求 → 计算 → 结果

有缓存：
请求 → Cache → 结果
          ↓ miss
        计算 → 写回

它是在做空间换时间：用额外的空间存储过去的计算，换取未来更低的延迟。

而懒加载、分页、流式计算，则是反方向的时间换空间：不要一次性准备所有东西，只在真正需要时计算。

七、第六大类：异步化——把“现在必须完成”改成“最终完成”

同步调用要求调用者等待结果；异步化则增加一个缓冲边界。

同步：
A ─────────→ B ─────────→ C
        等待

异步：
A → Queue → B
             ↓
             C

消息队列、事件总线、Pub/Sub、Kafka、任务系统，本质都在做类似的事情：

  • 把生产和消费解耦。
  • 把时间耦合变成消息耦合。
  • 允许上下游以不同速度运行。
  • 提供缓冲、重试、回放或削峰能力。

因此队列不只是“异步工具”，更像是一个时间维度上的间接层。

八、第七大类：背压与限流——不是所有请求都值得立即处理

异步化以后，新的问题出现了：生产速度可能超过消费速度。

Producer  ───────→  Queue  ─────→ Consumer
    1000/s            ↑             100/s
                      │
                   堆积 900/s

于是出现限流、背压、丢弃、采样、优先级队列、Admission Control、Token Bucket、Leaky Bucket。

它们背后的共同思想是：

系统容量是有限的，所以必须主动决定“什么进入系统、什么时候进入、进入多少”。

这和“广进严出”又形成一个有趣的对偶：前者解决输入压力，后者解决计算成本。

九、第八大类：重试、幂等、补偿——承认失败是正常状态

分布式系统里最危险的假设之一，是“调用要么成功，要么失败一次”。现实更接近：

请求
 ↓
超时？
 ↓
网络断开？
 ↓
服务已执行但响应丢失？
 ↓
重试？

于是形成一组经典组合：

  • Retry：再试一次。
  • Backoff：不要立即疯狂重试。
  • Idempotency：重复执行不会产生重复副作用。
  • Deduplication：识别重复请求。
  • Compensation：已经发生的动作无法回滚时，用新的动作补偿。
  • Dead Letter Queue：把暂时处理不了的消息隔离。

这里的更底层思想是：不要设计一个“永不失败”的系统，而要设计一个“失败后仍然可恢复”的系统。

十、第九大类：隔离——让失败不要扩散

熔断、舱壁、线程池隔离、租户隔离、进程隔离、容器、沙箱、安全域，本质都在回答一个问题：

如果这里坏了，能不能只坏这里？

没有隔离：
A → B → C → D
        ↓
       故障
        ↓
   全链路雪崩

有隔离：
A → [B]  ×
A → [C]  ✓
A → [D]  ✓

这是一种非常重要的复杂系统思想：控制故障的传播半径。

十一、第十大类：冗余与复制——不要让单点承担全部风险

主从、多副本、多活、备份、纠删码、RAID、重试，其实都在不同层面使用冗余。

冗余可以换来：

  • 可用性
  • 吞吐
  • 容灾能力
  • 数据持久性
  • 更低的尾延迟

但冗余也会带来一致性成本。所以分布式系统经常在“复制”和“一致性”之间做交换。

十二、第十一大类：状态与版本——不要只保存“现在”，还要知道它怎么来的

版本号、乐观锁、事件溯源、Append-only Log、MVCC、Snapshot、Checkpoint，都属于这一类。

State(t0)
   ↓ event
State(t1)
   ↓ event
State(t2)
   ↓ event
State(t3)

如果系统只保存最终状态，很多历史信息会消失；如果保存变化过程，就可以回放、审计、恢复、调试甚至重新计算。

这也是为什么 Git、Kafka Log、Event Sourcing、Agent Checkpoint 在思想上存在相似性：把“状态”变成可以追踪的时间序列。

十三、第十二大类：声明式——描述“我要什么”，而不是“怎么做”

命令式：

先创建容器
再挂载网络
再启动进程
再检查状态

声明式：

我要：
3 个副本
镜像 X
暴露端口 Y

然后由系统负责把当前状态逐渐逼近目标状态。

Kubernetes 是最典型的例子。Controller 持续执行：

Desired State
      ↓
Observe Current State
      ↓
Calculate Gap
      ↓
Action
      ↓
Observe Again
      ↺

这实际上已经非常接近 Agent Runtime 的核心闭环：目标状态 → 观察 → Gap → 行动 → 再观察。

十四、第十三大类：控制面与数据面——把“决定”与“执行”分开

这是我认为特别值得迁移到 Agent 的一种架构思想。

Control Plane
    │
    │ policy / scheduling / routing
    ↓
Data Plane
    │
    │ execution
    ↓
Environment

传统基础设施中，控制面可以相对低频地做全局决策，数据面则高频执行。这样既保证了全局治理能力，又避免每一次数据请求都重新做复杂决策。

Agent Runtime 也可以出现类似分层：

Agent Control Plane
  ├─ Policy
  ├─ Model Routing
  ├─ Memory Strategy
  ├─ Risk / Permission
  ├─ Scheduling
  └─ Evaluation
          ↓
Agent Runtime / Data Plane
  ├─ Tool
  ├─ Sandbox
  ├─ Browser
  ├─ Code Execution
  └─ External Systems

这不是说 Agent 必然采用这种架构，而是说明：“决策”和“执行”在复杂系统里往往会自然分离。

十五、第十四大类：声明、类型与契约——让错误尽可能提前暴露

类型系统、Schema、API Contract、静态检查、编译器、契约测试，背后有一个共同目标：

不要等到系统运行很久以后，才发现输入从一开始就不合法。

于是形成一种“左移”的思想：

运行时错误
   ↓
集成测试发现
   ↓
单元测试发现
   ↓
静态检查发现
   ↓
类型系统直接禁止

越靠左，修复成本通常越低。

这与“广进严出”非常接近，只不过过滤发生在时间轴上，而不是请求链路上。

十六、第十五大类：Fail Fast 与 Graceful Degradation——错误也要有策略

两个看似相反的原则，其实分别适用于不同场景。

Fail Fast：错误越早暴露越好。

Invalid Input
    ↓
立即拒绝

Graceful Degradation：非核心能力失败时，不要让整个系统一起失败。

完整服务
 ↓ 部分失败
核心能力仍然可用
 ↓
降级结果

二者可以同时存在：对不合法的输入 Fail Fast，对可恢复的局部故障 Graceful Degradation。

十七、第十六大类：可观测性——系统必须知道自己发生了什么

Logs、Metrics、Tracing、Audit、Event Stream，看起来是运维工具，实际上对应一个更底层的设计思想：

没有观察，就没有可靠的反馈；没有反馈，就无法控制复杂系统。

因此：

Observe
   ↓
Understand
   ↓
Decide
   ↓
Act
   ↓
Observe again

这与控制论、强化学习、Kubernetes Controller、Agent Loop 有非常强的结构相似性。

十八、第十七大类：反馈闭环——从“一次调用”变成“持续逼近目标”

很多传统程序可以近似理解成：

Input → Function → Output

而更复杂的系统逐渐变成：

Goal
 ↓
Action
 ↓
Environment
 ↓
Observation
 ↓
Evaluation
 ↓
Correction
 ↺

CI/CD、自动扩缩容、控制系统、推荐系统、强化学习、Agent Runtime 都在不同程度上使用这个结构。

我甚至会把它看成现代软件系统越来越重要的一条分界线：

函数式系统主要回答“给定输入，输出什么”；闭环系统开始回答“距离目标还有多远，以及下一步怎么办”。

十九、第十八大类：单调性——让系统尽可能只向“更接近目标”的方向移动

这是一个不那么常被当作设计模式讨论、但非常重要的思想。

例如：

  • Append-only Log：只追加，不修改历史。
  • 消息 offset：处理位置单调向前。
  • 版本号：新版本通常大于旧版本。
  • Checkpoint：恢复点沿时间推进。
  • Compaction：状态逐渐收敛。
  • Kubernetes Controller：不断缩小 Desired / Current Gap。

如果一个系统可以把复杂状态转换成某种单调进展，那么恢复、并发和推理都会容易很多。

二十、第十九大类：不可变性与复制——少修改共享状态

共享可变状态是并发系统最难处理的问题之一。

因此软件工程不断发明各种替代方案：

  • Immutable Object
  • Copy-on-Write
  • Persistent Data Structure
  • Event Sourcing
  • MVCC
  • Actor Model
  • CRDT

共同方向是：减少多个主体同时修改同一份状态的机会。

二十一、第二十大类：最小权限与能力边界——默认不要给全部能力

Least Privilege、Capability Security、Sandbox、RBAC、ABAC、Zero Trust 都可以放进这个框架。

主体
 ↓
身份
 ↓
能力
 ↓
资源范围
 ↓
动作范围
 ↓
执行

这也是 Agent Runtime 特别重要的设计思想：一个 Agent 能看到什么、能调用什么、能写哪里、能不能联网、能不能执行代码，不应该由“模型想做什么”单独决定，而应该由运行时的能力边界约束。

二十二、第二十一大类：插件化与组合——把系统变成“可扩展的积木”

Plugin、SPI、Dependency Injection、Strategy、Provider、Tool、Skill 都属于这个方向。

其核心不是“方便扩展”这么简单，而是：

把变化点显式化，让系统的稳定部分负责组合，而不是负责知道所有实现。

这也是 Agent Tool / Skill 设计里非常重要的原则：Runtime 不应该把所有能力硬编码进核心，而应该定义稳定的能力协议，让不同 Tool、Skill、Model、Provider 可以被动态组合。

二十三、第二十二大类：渐进式复杂化——先解决简单情况，再增加机制

很多优秀系统并不是一开始就把所有能力设计进去，而是：

Simple Case
   ↓
Boundary Case
   ↓
Failure Case
   ↓
Scale Case
   ↓
Distributed Case

例如：

  • 单机 → 多线程 → 多进程 → 分布式
  • 同步 → 异步 → 消息队列 → 分布式事件
  • 单模型 → 模型路由 → 多模型 → Agent Runtime
  • 单 Agent → Tool → Multi-Agent → Agent Society

每一步都是在真实复杂度出现之后增加新的抽象。

这其实是在遵循一个很朴素的原则：不要为尚未出现的复杂度提前支付全部成本。

二十四、把这些思想放在一起：软件工程其实一直在做什么？

如果把前面的几十种模式压缩一下，我会得到下面这张“软件设计原语地图”：

                    软件设计
                       │
       ┌───────────────┼───────────────┐
       ↓               ↓               ↓
     改变边界         改变时间         改变信息
       │               │               │
  抽象 / 代理       缓存 / 异步       过滤 / 索引
  隔离 / 分层       预计算 / 延迟     压缩 / 聚合
  模块 / 服务       重试 / 补偿       召回 / 精排
       │               │               │
       └───────────────┼───────────────┘
                       ↓
                    控制复杂度
                       ↓
                 观察 → 决策 → 行动
                       ↺

从这个角度看，软件工程的大量设计其实可以归结成几种动作：

  1. 隔离：让变化和故障不要传播。
  2. 拆分：降低局部复杂度。
  3. 抽象：隐藏不稳定实现。
  4. 过滤：让昂贵计算只发生在小候选集。
  5. 缓存：复用过去的计算。
  6. 延迟：把不必要的现在工作推到真正需要的时候。
  7. 异步：解除时间耦合。
  8. 复制：用冗余换可靠性与吞吐。
  9. 版本化：让变化可追踪、可恢复。
  10. 契约化：让错误尽可能提前暴露。
  11. 声明式：描述目标，让系统负责逼近目标。
  12. 反馈：通过观察不断修正行为。

二十五、一个更有意思的统一视角：这些设计都在管理“复杂度”

复杂度并不只有一种。

复杂度常见手段
结构复杂度分层、模块化、DDD、抽象
时间复杂度缓存、索引、预计算、并行
空间复杂度压缩、分片、流式、懒加载
并发复杂度Actor、队列、不可变性、锁、隔离
故障复杂度重试、熔断、降级、补偿、冗余
认知复杂度抽象、封装、Facade、契约
决策复杂度粗到精、分层决策、策略路由
变化复杂度版本、插件、DI、Adapter、Feature Flag
不确定性反馈、观测、实验、灰度、回滚

所以我越来越倾向于把架构设计理解成：

Architecture is the art of placing complexity where it can be controlled.

架构不是消灭复杂度。复杂度通常不会消失，只会被转移、分摊、延迟、隔离、隐藏或者显式化。

二十六、为什么这些思想在 Agent 时代会重新组合

传统软件大部分时候是确定性逻辑：

Input → Code → Output

Agent 系统则越来越像：

Goal
 ↓
Model Decision
 ↓
Tool / Environment
 ↓
Observation
 ↓
Evaluation
 ↓
New Context
 ↓
Next Decision
 ↺

于是过去的软件工程里的“隐形语法”开始重新组合：

  • 抽象层 → Tool / Skill / Provider / Model Adapter。
  • 粗到精 → Intent → Retrieval → Planning → Execution → Verification。
  • 缓存 → Context Cache / KV Cache / Memory / Trajectory。
  • 异步 → Event Bus / Task Queue / Agent Message。
  • 隔离 → Sandbox / Tenant / Permission Boundary。
  • 版本化 → Checkpoint / Resume / Conversation State。
  • 反馈闭环 → Observe → Evaluate → Optimize。
  • 控制面 → Agent Scheduler / Policy / Model Routing / Risk Control。
  • 声明式 → Goal / Desired State / Agent Specification。
  • 多主体 → Multi-Agent / Actor / Agent Society。

因此，Agent Runtime 并不是凭空出现的一种新软件。它更像是把过去几十年软件工程中关于调度、隔离、状态、反馈、资源管理和分布式系统的思想，重新组合到一个具有“决策能力”的执行实体周围。

二十七、但所有“万能思想”都有反模式

真正值得警惕的是把这些原则机械化。

万能药它带来的新问题
加一层链路更长、延迟更高、排查更难
加缓存一致性、失效、内存成本
加队列堆积、顺序、重复消费
加重试雪崩、重复副作用
加副本一致性和运维成本
加微服务网络、部署、观测、事务复杂度
加抽象认知负担、泄漏抽象
加 Agent不确定性、成本、验证难度
加反馈控制回路振荡、错误反馈放大

所以工程上的真正问题从来不是“有没有这个模式”，而是：

这个模式把复杂度从哪里搬到了哪里？它降低了什么成本，又增加了什么成本？

二十八、我现在更喜欢用这七个问题检查一个架构

  1. 边界在哪里？ 谁和谁不应该直接耦合？
  2. 复杂度在哪里？ 是结构、时间、并发、故障还是决策复杂度？
  3. 昂贵决策能否后置？ 能不能先粗筛，再精算？
  4. 结果能否复用？ 能不能缓存、索引、预计算？
  5. 失败能否局部化？ 一个组件坏了，传播半径多大？
  6. 状态能否恢复？ 有没有版本、日志、Checkpoint、Replay？
  7. 系统能否反馈？ 它怎么知道自己做得对不对？

如果一个系统能够很好地回答这七个问题，很多具体的技术选择反而会变得容易。

二十九、最后：我觉得“设计模式”可能只是表面

Design Pattern 给了我们很多名字：Adapter、Facade、Proxy、Strategy、Observer、Chain of Responsibility、Circuit Breaker、Saga……

但如果只记名字，很容易变成“看到问题就套模式”。

如果把这些模式往下抽象一层，会看到更少、更稳定的东西：

                软件设计
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
      边界         时间         信息
       │           │           │
    隔离/抽象    延迟/异步    过滤/聚合
    拆分/代理    缓存/重试    索引/压缩
       │           │           │
       └───────────┼───────────┘
                   ↓
               复杂度管理
                   ↓
               反馈与控制
                   ↺

也许这才是我理解的软件工程里更底层的“隐形语法”。

好的架构，不是堆积更多组件，而是不断把问题变成更容易控制的问题。

“加一层”与“广进严出”只是其中两个非常漂亮的缩写。

而当 Agent 开始进入软件系统之后，我觉得这张地图还会继续扩张：过去我们主要设计“程序如何执行”，现在开始设计“一个会决策的系统如何在不确定环境里持续执行、验证、修正和演化”。

这也许正是 Agent Runtime 最值得研究的地方。
