# Grill Me、Superpowers 与 OpenSpec：把 AI 编程从“会写代码”变成可控的工程流程

## 先给结论：三者不是三个同类工具

最近在思考如何把本地 Coding Agent CLI 串成一条完整的工程链路：从需求梳理、方案设计、计划拆解，到编码、Judge、CI/CD，最后再到发布和部署。Grill Me、Superpowers 和 OpenSpec 都能参与这条链路，但它们解决的不是同一个问题。

我的判断是：

- **Grill Me：把问题问透。** 通过连续追问，逐个消除方案里的隐含假设和未决选择。
- **Superpowers：把开发过程做扎实。** 它是一套面向 Coding Agent 的工程方法与可组合 Skills，覆盖设计讨论、计划、TDD、代码审查、调试和完成前验证。
- **OpenSpec：把需求和变更变成可追踪的规格资产。** 它用结构化的 proposal、specs、design、tasks 等工件，让人和 Agent 在编码前对“要改什么、怎样算完成”达成一致。

因此，它们更像是三个互补维度：**决策澄清、执行方法、规格治理**。它们有重叠，但不应该机械地当成三个必须按顺序运行的独立阶段。

## 一、Grill Me：消除需求和设计中的隐含假设

Grill Me 是 Matt Pocock 的 Skills 集合中的一个技能。它的核心指令很简洁：持续访谈用户，沿着设计决策树逐项深入，每次只问一个问题，并为问题提供建议答案。它本身不是一套完整的软件开发生命周期，也不是规格管理器。

官方来源：[mattpocock/skills · grill-me](https://github.com/mattpocock/skills/tree/main/skills/productivity/grill-me)。

### 它解决什么问题？

自然语言需求通常只描述了用户想到的表层目标，关键约束却藏在默认假设里。例如：

> 我想做一个本地 CLI，让它调用 Pi Agent、Cursor CLI 和 DeepSeek，完成需求到发布的自动化流程。

这句话仍然留下许多影响架构的决策：

- CLI 是一个流程编排器，还是一个长期运行的 Agent Runtime？
- Pi 和 Cursor 是可替换的执行 Provider，还是各自负责固定阶段？
- DeepSeek 是主模型、Judge，还是成本较低的候选模型？
- 计划由谁批准？哪些步骤可以自动执行？
- 修改代码后，测试失败可以自动重试几次？什么情况必须停止并交给人？
- 发布和部署是否允许自动执行？生产环境是否必须人工审批？

Grill Me 的价值不是立即替你选择架构，而是把这些决策逐个暴露出来，问清楚选择背后的理由和边界。它尤其适合方案还不成熟、决策之间存在依赖、错误假设会导致大量返工的阶段。

### 它不擅长什么？

Grill Me 不会天然为项目建立一套长期规格目录，也不负责保证每个实现任务遵循 TDD，更不会因为追问结束就证明设计正确。回答仍然可能不完整，用户也可能暂时无法决定。

因此，结束条件不应是“已经问了很多问题”，而应该是：**影响实现的关键决策已明确；未知项已标注；剩余风险有明确的验证方式或负责人。**

如果代码库已经包含答案，就应先查代码、配置、测试和文档，而不是把用户当成唯一的信息源。这一点也很重要：追问应补足证据，而不是制造额外对话成本。

## 二、Superpowers：把工程纪律嵌入 Coding Agent 的工作方式

Superpowers 是 obra 维护的 Agentic Skills 框架和软件开发方法论。它不只是一个“先写计划”的提示词，而是一组相互配合的工作技能。

官方仓库：[obra/superpowers](https://github.com/obra/superpowers)。

它的典型流程包括：

1. **Brainstorming**：在开始实现前澄清目标、探索方案、形成设计并获得确认。
2. **Writing Plans**：把设计拆成细粒度、可检查的任务，写明文件、步骤和验证方式。
3. **执行计划**：通过逐任务执行或子 Agent 驱动开发来推进实现。
4. **Test-Driven Development**：遵循 Red → Green → Refactor，先看到失败测试，再实现最小改动。
5. **Review 与 Debugging**：系统性定位问题，对照计划检查实现，并在任务完成前验证。
6. **Finishing**：验证分支状态，给出合并、PR 或保留分支等明确的收尾选择。

它最重要的贡献，是把工程实践变成 Agent 工作时的行为约束，而不是只写在团队规范里的建议。比如“测试通过了”不能仅凭模型自述；应运行真实命令、读取退出码和结果，再作出完成判断。

### Superpowers 与 Grill Me 的重叠

Superpowers 的 Brainstorming 本身也会通过提问来澄清需求，和 Grill Me 有明显交集。区别在于关注点：

- Grill Me 是一种可以显式调用的深度访谈技能，适合沿决策树把某个计划问透。
- Superpowers 的 Brainstorming 是整个工程方法的一环，最终要把理解收敛为设计，并继续连接计划和实施。

所以，不是每次都要先运行 Grill Me，再让 Superpowers 的 Brainstorming 把同样的问题问一遍。对于简单需求，可以直接使用 Superpowers；对于架构影响大、风险高或用户自己也还没想清楚的需求，再用 Grill Me 深挖。

### 它也不是规格数据库

Superpowers 可以产出设计文档和执行计划，但它的核心价值是执行方法和工程纪律，不是维护跨变更的需求基线、规格演进和变更归档。若项目需要长期回答“这个系统承诺了什么行为”“本次变更修改了哪条需求”“规格与实现是否一致”，就需要更明确的规格治理方式。

## 三、OpenSpec：让变更拥有可审查、可演进的规格

OpenSpec 是面向 AI Coding Assistant 的 Spec-Driven Development 工具。它把一次变更的意图、需求、设计和任务放进结构化工件中，而不是让它们只存在于聊天记录里。

官方仓库：[Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)，文档：[openspec.dev/docs](https://openspec.dev/docs)。

一个典型的变更目录会包含：

- `proposal.md`：为什么要做、要改变什么。
- `specs/`：系统行为要求，以及可用于检验的场景。
- `design.md`：技术方案和重要设计决策。
- `tasks.md`：实现任务清单。
- 归档后的变更记录：保留已完成变更的历史，并在适用时更新当前规格。

例如，“失败后支持断点恢复”不应只有一句需求。规格可以进一步写明：任务执行到某一步后进程退出；恢复时读取最近一次有效 Checkpoint；已经成功完成且具备幂等保证的步骤不应重复产生外部副作用；状态不兼容时必须明确失败，而不能假装恢复成功。

这种结构有两个价值。第一，规格能在编码前被人审查。第二，后续的编码 Agent、Judge 和 CI 检查可以引用同一组行为要求，而不必从长对话中重新猜测验收标准。

### OpenSpec 不是“文档越多越好”

OpenSpec 强调可迭代的规格工作流，并不是要求每次改一行代码都建立完整文档。对于小型、低风险的改动，过度规格化会增加维护成本。更合理的做法是根据变更风险决定规格粒度：

- 文案、局部样式、小型修复：简短任务说明和验证即可。
- 新功能、API 行为变化、数据模型变化：明确需求场景、设计和验收条件。
- 权限、计费、数据迁移、生产发布、长周期任务恢复：必须把失败场景、兼容性、安全边界和回滚策略写清楚。

规格不是为了让流程显得严谨，而是为了减少错误理解造成的返工，并让正确性能够被验证。

## 四、三者的核心差异

| 维度 | Grill Me | Superpowers | OpenSpec |
|---|---|---|---|
| 核心问题 | 我们到底要解决什么？还有哪些决定没想清楚？ | Agent 应按什么工程方法完成工作？ | 系统行为和本次变更如何被明确记录、审查和追踪？ |
| 主要形态 | 深度访谈 Skill | Skills 框架 + 开发方法论 | 规格驱动的变更工作流与 CLI |
| 主要产物 | 已澄清的决策、假设、未决项 | 设计、实施计划、测试、审查与验证结果 | Proposal、Specs、Design、Tasks、归档变更 |
| 对编码的影响 | 间接：减少错误理解 | 直接：约束计划、编码、测试和审查过程 | 间接且持续：用规格约束实现并保留变更历史 |
| 验证机制 | 主要验证理解是否充分 | 强调真实测试、代码审查和完成前验证 | 将验收场景和规格变更作为可追踪依据 |
| 最适合 | 复杂、模糊、决策依赖多的需求 | 希望 Agent 稳定遵循工程纪律的开发任务 | 多阶段、长期演进、需要可审查变更记录的项目 |
| 不能替代 | 技术调研、规格存储、测试 | 业务决策、持久化规格治理 | 真实测试、代码质量审查、运行时安全控制 |

简化来说：

- Grill Me 提高**需求理解的质量**。
- Superpowers 提高**执行过程的质量**。
- OpenSpec 提高**变更表达、审查和追踪的质量**。

这不是严格互斥的分类。Superpowers 的 Brainstorming 和 OpenSpec 的 Explore 都可以帮助探索需求；Superpowers 也能写计划，OpenSpec 也有任务清单。真正的区别不在于它们有没有某个相似功能，而在于各自的主责和最终留下什么可复用的资产。

## 五、如何组合：以本地 Coding Agent CLI 为例

我倾向于把它们放进一个更大的开发闭环，而不是简单地把三个工具串起来就认为系统可靠。

```text
需求 / Issue / 用户想法
          │
          ▼
  读取现有代码、配置、测试和文档
          │
          ▼
 Grill Me（按需）
 澄清目标、约束、决策与未知项
          │
          ▼
 方案确认 / 选择实现路径
          │
          ▼
 OpenSpec（中高风险变更）
 Proposal + Specs + Design + Tasks
          │
          ▼
 Superpowers
 细化实施计划 → TDD → 编码 → Review
          │
          ▼
 Judge / 独立验收
 对照规格检查行为与证据
          │
          ▼
 CI/CD：测试、静态检查、构建、安全扫描
          │
          ▼
 人工审批（高风险发布）→ 部署 → 运行观测
          │
          ▼
 反馈、问题记录、规格与后续任务更新
```

### 1. 需求入口：先调查，再决定是否追问

CLI 收到需求后，不应马上调用模型生成一份大计划。先检索仓库、相关模块、已有测试和项目约定，确认系统当前状态。

如果需求仍有关键歧义，再调用 Grill Me，一次只处理一个高价值问题。每个决策可以记录为：

- 已确认：用户明确认可。
- 推断：Agent 根据代码或惯例作出的判断，需要标注证据。
- 未决：当前无法决定，需要实验、调研或人工选择。
- 非目标：本次明确不做什么。

这样可以避免把模型的默认选择伪装成用户已确认的要求。

### 2. 规格阶段：让 OpenSpec 承接长期有效的变更事实

如果变更涉及多个模块、接口行为、数据结构或安全边界，就建立 OpenSpec change。需求场景应当可观察、可测试，设计记录关键取舍，任务清单标出依赖和验证方式。

不要把所有聊天内容都塞进规格。规格应该记录**实现必须遵守的行为与约束**；临时讨论、被否决的方案和长篇探索过程可以留在其他记录中。

### 3. 实施阶段：由 Superpowers 保证工程过程

Superpowers 的计划应细到每个任务都有清楚的改动目标和检查方式。实现过程中先写失败测试，再写最小实现，然后重构；完成一个任务后，按需进行规格符合性和代码质量两类审查。

如果 OpenSpec 已经维护 `tasks.md`，就不应再维护一份长期漂移、内容重复的第二任务清单。可以让 OpenSpec 负责变更级任务状态，Superpowers 的计划负责更细粒度的执行步骤，并明确哪份是事实来源。

### 4. Judge 与 CI/CD：必须独立于“模型说完成了”

Judge 不应只问另一个模型“这段代码写得好吗”。更稳妥的验证顺序是：

1. 检查改动是否覆盖规格中的每个验收场景。
2. 运行单元测试、集成测试和必要的端到端测试。
3. 执行类型检查、Lint、构建和安全检查。
4. 检查差异、权限边界、数据迁移和副作用。
5. 对高风险行为要求人工审批。

模型 Judge 可以补充语义审查、寻找遗漏场景，但不能替代确定性测试和真实运行证据。CI 通过也不等于业务目标一定实现；还需要关注验收场景是否覆盖真实用户行为。

### 5. 发布阶段：自动化应由风险和权限决定

通过测试并不意味着可以无条件部署。开发环境可以更自动化；生产环境、数据迁移、计费和外部副作用应设置明确的权限门控、审批、回滚与审计记录。

把“是否能执行”与“是否被授权执行”分开。Agent 可以提出发布动作，但 Runtime 应检查当前环境、操作风险、用户授权和所需证据。

## 六、不要把三个工具的流程叠成三倍工作量

最常见的失败模式不是工具不够，而是重复产物太多：

- Grill Me 追问一次，Superpowers Brainstorming 再完整追问一次。
- OpenSpec 生成一份任务清单，Superpowers 又生成一份不一致的计划。
- 规格写了验收条件，但 Judge 使用另一套标准。
- CI 通过后，Agent 没有检查实际业务场景，却直接宣布完成。

要避免这些问题，关键是明确**每类信息只有一个权威来源**：

| 信息 | 建议的权威来源 |
|---|---|
| 用户确认的目标、范围和关键决策 | 需求记录 / 已确认设计 |
| 需要长期维护的行为要求 | OpenSpec Specs |
| 当前变更的技术方案与任务状态 | OpenSpec change；细粒度执行计划作为辅助 |
| 代码事实与当前实现 | 仓库代码、配置、测试 |
| 验证结果 | 测试、CI 日志、静态检查与运行证据 |
| 发布授权和操作记录 | Runtime 策略、审批记录和审计日志 |

另外，不是每次都必须三者全用。简单修改可以直接实施并验证；中等复杂度需求可以用 Superpowers；高歧义需求先用 Grill Me；长期演进或高风险变更再引入 OpenSpec。流程应随风险升级，而不是一律走最重路径。

## 七、如何把它们集成进自己的 Agent Runtime

如果将来把这套方式做进本地 CLI，我不会把三个工具简单写死成三段 Shell 命令，而会把它们视为可选择的能力模块，并由一个有状态的 Runtime 管理生命周期。

一个最小的任务状态机可以是：

```text
RECEIVED
  → RECONNAISSANCE
  → CLARIFYING（按需）
  → SPEC_READY（按需）
  → PLAN_APPROVED
  → IMPLEMENTING
  → VERIFYING
  → REVIEW_REQUIRED（按风险）
  → READY_TO_RELEASE
  → DEPLOYED
```

每次状态转换都应有进入条件和证据。例如，从 `VERIFYING` 进入 `READY_TO_RELEASE`，需要规定的测试通过、规格场景有验证结果、风险检查完成；生产发布还需要额外授权。

Runtime 至少需要保存：

- `task_id`、需求来源和代码版本；
- 已确认的决策、未决问题及其证据；
- OpenSpec change 标识和规格版本；
- 当前计划、任务依赖和执行状态；
- 每个步骤的输入输出、工具调用和失败分类；
- 测试命令、退出码、日志和 Judge 发现；
- 审批、发布记录、Checkpoint 与恢复信息。

失败时，系统不应该无差别重跑整条链路。需求不清楚应返回澄清；规格冲突应回到设计；测试失败应进入系统性调试；外部服务超时可以按策略重试；权限不足或生产发布则应停下来等待授权。

这才是从“会调用 Skills 的 CLI”走向“可恢复、可审计的 Coding Agent Runtime”的关键：**Skill 提供局部能力，规格提供行为依据，Runtime 管理状态与权限，验证系统提供证据。**

## 结语：把工具当作方法与资产，而不是仪式

Grill Me、Superpowers 和 OpenSpec 分别代表了三种值得保留的工程思想：认真澄清问题、严格执行工程方法、用规格管理变更。

它们的价值不在于让开发流程变得更长，而在于减少不同类型的不确定性：

- Grill Me 减少“做错了需求”的风险。
- Superpowers 减少“过程随意、测试缺失、没有证据就宣称完成”的风险。
- OpenSpec 减少“需求散落在聊天记录、变更难追踪、规格与实现逐渐漂移”的风险。

对于我的本地 Coding Agent CLI，推荐策略是：**先读取项目事实；有歧义时用 Grill Me；需要长期可追踪的变更时用 OpenSpec；实施时采用 Superpowers 的工程纪律；最后由独立验证、CI/CD、风险门控和发布观测形成闭环。**

最终目标不是把三个工具拼在一起，而是建立一套可以根据任务复杂度灵活选择、根据证据推进状态、在失败时安全恢复的工程系统。
