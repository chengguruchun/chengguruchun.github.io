# AI 全栈开发的前端语言：把页面需求说清楚的术语手册

## 为什么 AI 开发时代还要懂前端术语？

现在借助 AI 写一个页面，可能只需要一句话：“帮我做一个好看的后台管理系统。”模型很快就能生成页面。但“好看”“现代”“简洁”并不是可执行的规格：侧边栏是否固定？内容区是否需要最大宽度？筛选条件如何提交？表格是否支持分页？加载中、空数据和请求失败时显示什么？

这些没说清楚，AI 就只能自行补全。生成结果可能看起来不错，却和真正的产品需求相差很远。

因此，学习前端术语的价值不在于背诵名词，而在于获得一套**精确描述界面结构、视觉规则、交互行为和数据流的语言**。术语越准确，需求中的歧义越少；验收标准越明确，AI 生成的结果就越容易验证。

本文从全栈开发的实际沟通出发，整理常见概念，并进一步讨论如何把这些概念转化成 AI 能执行、开发者能检查的任务。

## 一、先建立前端的整体地图

可以先把一个 Web 页面理解为四个相互关联的层次：

```text
用户看到的页面
   │
   ├── 结构：HTML / DOM
   ├── 表现：CSS / Layout / Responsive
   ├── 行为：JavaScript / Events / State
   └── 数据：API / Request / Response
                │
                └── 后端服务、数据库与业务规则
```

- **HTML** 描述内容的语义结构，例如标题、表单、按钮、表格。
- **CSS** 决定元素的尺寸、颜色、间距、排布和不同屏幕下的呈现方式。
- **JavaScript / TypeScript** 负责交互逻辑、状态变化、数据处理与请求调用。
- **API** 让前端与后端交换数据。前端页面并不等于业务数据本身。

在现代框架中，开发者通常不会直接手写所有 DOM 操作，而是使用 React、Vue 等框架，通过组件、状态和数据驱动页面更新。但底层仍然离不开这些概念。

## 二、描述页面结构：元素、DOM、组件与语义

### 1. Element、Tag 与 DOM

- **Tag（标签）**：HTML 源码中的标记，例如 `<button>`、`<section>`。
- **Element（元素）**：浏览器解析 HTML 后形成的文档元素。
- **DOM（Document Object Model）**：浏览器把文档组织成可查询、可操作的树状对象结构。

例如，页面有一个标题和一个按钮。它们不仅是视觉上的两块内容，也处于 DOM 树中的不同节点。

对 AI 说“把右边那个东西调小一点”是不精确的；更好的描述是：“将用户详情卡片中的主操作按钮高度从 40px 调整为 32px，不改变卡片标题和其他按钮。”

### 2. Semantic HTML：语义化标签

`<main>`、`<nav>`、`<header>`、`<button>` 和 `<form>` 不只是不同外观的标签，它们表达不同的内容角色或交互含义。

当需求说“这是一个按钮”时，优先使用真正的 `button`，而不是把一个 `div` 装饰成按钮。语义正确有助于键盘操作、辅助技术、浏览器默认行为，也让代码更容易被人和 AI 理解。

### 3. Component：组件

组件是可复用的 UI 单元。常见例子包括：

- **Button**：按钮
- **Input**：输入框
- **Modal / Dialog**：模态弹窗
- **Dropdown / Select**：下拉菜单或选择器
- **Tabs**：标签页
- **Card**：卡片
- **Table / Data Grid**：表格或数据网格
- **Pagination**：分页器
- **Toast / Notification**：轻提示或通知
- **Sidebar**：侧边栏

“增加一个确认弹窗”比“再做一个小窗口”清楚；“复用现有的 ConfirmDialog 组件，点击确认后才提交请求，取消不产生副作用”则更接近可实施的开发任务。

**重要区别：组件是代码组织和复用单位，不等于页面上任意一个矩形。** 是否值得抽成组件，通常取决于复用、复杂度、状态边界和维护成本，而不是页面上有多少块区域。

## 三、描述布局：不要只说“摆得整齐”

布局术语能把模糊的视觉要求转成明确约束。

### 1. 常用布局概念

| 术语 | 含义 | 可用于需求的表达 |
|---|---|---|
| Container / Wrapper | 包裹内容并控制整体宽度的容器 | 内容区最大宽度 1200px，居中显示 |
| Flexbox | 一维布局，适合一行或一列中的对齐和分配 | 工具栏使用 Flex，标题靠左，操作按钮靠右 |
| CSS Grid | 二维布局，同时控制行与列 | 桌面端采用三列卡片网格，间距 24px |
| Gap | Flex/Grid 子项之间的间距 | 卡片之间使用 16px gap |
| Padding | 元素内容与边界之间的内边距 | 卡片内边距 24px |
| Margin | 元素外部的间距 | 页面标题下方留 20px |
| Alignment | 对齐方式 | 图标与文字垂直居中 |
| Overflow | 内容超出容器时的处理方式 | 表格横向溢出时允许容器滚动 |
| Position: sticky | 元素滚动到指定位置后保持粘附 | 表格表头在纵向滚动时保持可见 |

### 2. Flex 与 Grid 怎么选？

可以用一个简单原则：

- **Flexbox**：主要处理一个方向上的排列，例如导航栏、表单操作区、按钮组。
- **Grid**：需要同时规划行和列时更自然，例如统计卡片、图片墙、仪表盘。

不要只说“使用响应式布局”。最好补充断点和变化规则，例如：“宽度大于 1024px 时三列，小于 1024px 时两列，小于 640px 时单列。”

### 3. Responsive Design：响应式设计

响应式不是简单地把页面缩小，而是让布局、字号、间距和交互方式适应不同视口（Viewport）。

向 AI 描述响应式需求时，至少明确：

- 支持哪些设备或屏幕宽度；
- 哪些区域可以换行、折叠或隐藏；
- 表格在小屏幕下如何处理；
- 移动端导航是否改为抽屉菜单；
- 是否存在不能被压缩的最小宽度。

## 四、描述视觉样式：颜色只是其中一部分

### 1. Design Tokens：设计令牌

设计令牌是统一管理颜色、字号、间距、圆角、阴影等视觉变量的方式。例如：

```css
:root {
  --color-primary: #2563eb;
  --color-text: #1f2937;
  --color-muted: #6b7280;
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 12px;
  --radius-card: 12px;
}
```

与其让 AI 在每个组件里随意选择颜色和间距，不如要求它复用项目现有的设计令牌。这样页面更一致，后续调整也更容易。

### 2. Typography、Hierarchy 与 Contrast

- **Typography（字体排印）**：字体、字号、字重、行高和字距。
- **Visual Hierarchy（视觉层级）**：通过尺寸、位置、颜色和留白表达信息的重要程度。
- **Contrast（对比度）**：文字与背景之间的视觉差异，影响可读性和可访问性。
- **Whitespace（留白）**：元素周围有意保留的空间，不等于浪费空间。
- **Border Radius（圆角）**、**Shadow（阴影）**：塑造组件边界和层次的视觉属性。

“更高级一点”可以作为审美方向，但不能作为唯一验收标准。可以进一步说明：“页面以中性色为主，主操作使用统一的品牌色；标题、正文、辅助信息形成三级字号层次；卡片使用轻边框，不使用大面积投影。”

## 五、描述交互：事件、状态与反馈

页面不只是静态图片。交互需求应当描述用户动作、系统反应和最终状态。

### 1. Event：事件

点击、输入、提交、键盘操作、拖拽和滚动都可能触发事件。

例如：“点击搜索按钮后提交筛选条件”仍不够完整，还需要说明是否支持回车提交、是否允许重复点击，以及请求失败时如何提示。

### 2. State：状态

状态是决定当前 UI 如何显示的数据。例如：

- 当前选中的标签页；
- 搜索框内容；
- 表格当前页码；
- 弹窗是否打开；
- 请求是否正在进行；
- 用户是否有编辑权限。

在 React / Vue 等框架中，状态变化通常会驱动页面更新。描述需求时要区分**临时 UI 状态**和**业务数据状态**，不要把所有数据都混成一个“页面状态”。

### 3. Loading、Empty、Error 与 Success

一个完整的请求交互通常不只有成功路径，还应考虑：

- **Loading State**：请求进行中，显示加载提示或骨架屏；
- **Empty State**：请求成功，但没有数据；
- **Error State**：请求失败，提供错误提示和可行的恢复操作；
- **Success Feedback**：操作成功后的提示或页面更新；
- **Disabled State**：条件不满足时禁用控件，并在需要时解释原因。

这几个术语非常值得在 AI 需求中明确写出。否则，AI 往往只实现“理想情况下的成功路径”。

### 4. Modal、Drawer、Popover 与 Tooltip

它们看起来都像浮层，但用途不同：

- **Modal / Dialog**：需要用户集中处理的对话框，通常会阻断背景操作。
- **Drawer**：从页面边缘滑出的面板，适合详情、编辑或辅助导航。
- **Popover**：锚定某个元素显示的浮层，常用于轻量操作。
- **Tooltip**：悬停或聚焦时展示简短说明，不适合承载复杂交互。

如果需求涉及“点击行查看详情”，应明确使用侧边 Drawer、独立详情页还是 Modal，而不是让 AI 自行猜测。

## 六、描述数据流：前端不是孤立的页面

### 1. API、Request、Response

前端通常通过 HTTP 请求后端 API。描述一个页面功能时，需要明确：

- 请求何时发起；
- 请求方法和接口约定；
- 参数从哪里来；
- 返回数据如何映射到界面；
- 失败时如何处理；
- 是否需要分页、排序或筛选；
- 权限和身份信息如何沿用项目现有机制。

如果后端接口还不存在，应明确这是“先用 Mock Data 实现页面”还是“需要同时设计并实现后端接口”。两者的工作范围完全不同。

### 2. Mock Data：模拟数据

Mock Data 用于在后端尚未就绪时验证页面布局和交互。它不应被误认为真实业务数据。

可明确要求：“先用本地 Mock Data 实现表格、分页和空状态；把数据访问封装在独立模块中，后续接入真实 API 时不重写页面组件。”

### 3. Pagination、Sorting 与 Filtering

- **Pagination**：分页，常见有页码分页和游标分页。
- **Sorting**：排序，例如按创建时间倒序。
- **Filtering**：筛选，例如按状态、日期范围过滤。
- **Search**：搜索，通常基于关键词匹配。
- **Debounce（防抖）**：停止输入一段时间后再触发操作，适合搜索框。
- **Throttle（节流）**：在一段时间内限制触发频率，适合某些高频事件。

还要说清楚这些操作发生在前端还是后端。数据量很小时可以前端筛选；数据量较大时通常应由后端分页和筛选，不能只在当前页数据上做“全量筛选”。

## 七、路由、权限与表单

### 1. Routing：路由

路由决定 URL 对应哪个页面或视图。常见需求包括：

- 点击菜单进入指定路由；
- 刷新页面后仍能访问当前路径；
- 支持通过 URL 参数还原筛选条件；
- 未登录时跳转登录页；
- 未授权时显示无权限页面。

路由（Routing）和导航（Navigation）相关，但并不是同一个概念：路由定义地址与页面的映射，导航是用户在页面之间移动的交互方式。

### 2. Authentication 与 Authorization

- **Authentication（认证）**：确认“你是谁”，例如登录和身份校验。
- **Authorization（授权）**：判断“你能做什么”，例如是否允许编辑或删除。

只在前端隐藏按钮不构成真正的权限保护。敏感操作必须由后端进行权限校验；前端权限控制主要用于正确呈现界面与交互。

### 3. Form Validation：表单校验

需要说明哪些字段必填、格式是什么、错误提示放在哪里、何时校验，以及提交期间如何防止重复操作。

例如：“邮箱在失焦时校验格式，提交时执行完整校验；错误提示显示在字段下方；提交期间禁用按钮；后端返回的字段错误映射到对应输入框。”

## 八、工程术语：让 AI 在现有项目里正确修改

AI 开发不只是生成新页面，更多时候是在已有代码中增量修改。以下术语有助于限定改动边界：

- **Component Reuse**：优先复用已有组件，避免重复实现。
- **Props**：父组件向子组件传递的参数。
- **State Management**：管理跨组件或跨页面共享状态的机制。
- **Lifecycle / Effect**：组件挂载、更新或响应依赖变化时执行的逻辑；具体含义取决于框架。
- **TypeScript Types / Interfaces**：描述数据结构与接口约束，帮助更早发现不匹配。
- **Dependency**：代码或模块依赖的其他能力。
- **Build**：把源码处理成可运行或可部署产物的过程。
- **Lint / Format**：检查代码规则、统一格式。
- **Unit Test / Integration Test / E2E Test**：分别验证单元、模块协作和完整用户流程。
- **Regression**：修改后原有功能意外损坏。

给 AI 的任务最好包含边界：“先阅读项目结构和现有组件；沿用当前框架、样式方案和请求封装；只修改用户管理页面及必要的共享组件；不要擅自升级依赖或重构无关模块。”

## 九、包管理与依赖治理：依赖不是“装上就行”

前端项目很少只靠浏览器原生能力。组件库、路由、请求客户端、构建工具、测试框架，通常都通过包管理器引入。这里的术语直接影响 AI 能否安全地修改一个已有项目。

### 1. Package Manager、Package 与 Registry

- **Package（软件包）**：可被项目引用和复用的代码及其元数据。
- **Package Manager（包管理器）**：负责安装、卸载、升级依赖，并处理依赖关系，例如 npm、pnpm、Yarn。
- **Registry（包仓库）**：发布和下载软件包的服务，例如 npm registry 或企业私有 registry。
- **Dependency（依赖）**：项目运行或开发时需要的外部包。
- **Transitive Dependency（传递依赖）**：依赖的依赖。你只安装一个包，安装树可能因此引入几十个其他包。

### 2. package.json、Lockfile 与可复现安装

- **package.json**：项目元数据、脚本、直接依赖和版本范围。
- **Lockfile**：锁定完整依赖树中的具体版本与解析结果。常见文件包括 `package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`。
- **Deterministic / Reproducible Install（确定性 / 可复现安装）**：开发者本机、CI 和发布环境尽可能安装到一致的依赖树。
- **Semantic Versioning / SemVer（语义化版本）**：常见版本格式为 `MAJOR.MINOR.PATCH`。通常主版本代表不兼容变化，次版本代表向后兼容的功能增加，补丁版本代表向后兼容的问题修复；但仍需阅读具体包的发布说明。

一个重要区别是：`^1.2.3` 是允许版本范围，不代表每次安装都会固定到 1.2.3；lockfile 才会进一步锁定实际解析结果。因此，AI 修改依赖时，不应只看 package.json 有没有变化，还要检查 lockfile 是否同步、依赖树是否出现非预期升级。

### 3. dependencies、devDependencies 与 peerDependencies

- **dependencies**：应用运行时需要的依赖。
- **devDependencies**：构建、测试、Lint 等开发阶段使用的依赖。
- **peerDependencies**：声明当前包预期由宿主项目提供的兼容依赖，组件库和插件中尤其常见。

例如，一个 React 组件库可能把 React 声明为 peer dependency，避免把另一份 React 一起打包进去。安装警告不应一律通过强制安装或忽略冲突来消除；先弄清楚版本冲突来自哪里。

### 4. 常见包管理命令背后的工程含义

| 术语 / 命令 | 含义 | 需要注意 |
|---|---|---|
| install | 安装依赖 | 可能按 lockfile 解析并更新依赖树 |
| frozen / immutable install | 严格按 lockfile 安装 | CI 中可避免锁文件与清单不一致时悄悄漂移 |
| add / remove | 添加或移除依赖 | 同时检查包体积、许可证、维护状态和安全风险 |
| update / upgrade | 升级依赖 | 区分补丁升级与可能包含破坏性变化的主版本升级 |
| peer dependency conflict | 宿主依赖版本不兼容 | 不要未经分析就用强制参数压掉警告 |
| audit | 检查已知依赖漏洞 | 结果需要结合可利用性、修复版本和项目风险判断 |

**给 AI 的约束可以这样写：**“先检查当前包管理器和 lockfile；优先使用项目已有依赖；确实需要新包时解释引入原因和替代方案；不要混用 npm、pnpm、Yarn，不要删除或重建 lockfile 来规避冲突；完成后执行项目已有的安装、类型检查、Lint 和测试命令。”

## 十、构建与工程化：代码能运行，不等于能上线

“页面在我电脑上能打开”只证明了一个局部环境里的开发结果，不代表产物能在生产环境正确运行。全栈开发还需要理解从源码到线上服务的交付链路。

### 1. Build、Bundle、Transpile 与 Tree Shaking

- **Build（构建）**：执行编译、资源处理、打包和优化，生成运行或部署所需的产物。
- **Transpile（转译）**：把某种语法或语言转换为目标环境能理解的形式，例如 TypeScript 转成 JavaScript。
- **Bundle（打包）**：将模块及其依赖组织成一个或多个输出文件。
- **Tree Shaking**：在静态分析可行的前提下，移除未使用的导出代码。
- **Code Splitting（代码分割）**：把代码拆成多个加载单元，减少初始页面必须下载的资源。
- **Source Map**：把压缩或转译后的代码映射回源码，帮助定位生产错误；是否公开给浏览器需要结合安全和运维策略。

构建成功并不等于功能正确。它只能证明构建工具接受了当前输入；接口契约、权限、交互、兼容性和业务规则仍然需要验证。

### 2. Environment、Configuration 与 Secret

- **Environment（环境）**：开发、测试、预发布、生产等不同运行环境。
- **Environment Variable（环境变量）**：部署时注入的配置，例如 API Base URL。
- **Configuration（配置）**：影响应用行为但不一定属于业务代码的参数。
- **Secret（秘密信息）**：Token、密码、私钥等敏感数据。

前端构建工具中的变量往往会被编译进公开的静态资源。**不能把私钥、数据库密码或服务端 Token 放进前端环境变量并以为它们是安全的。** 任何发送到浏览器的内容，都应默认可被用户查看。

需求里应明确：“开发、预发布和生产环境使用正确的 API 地址；敏感凭据仅保存在服务端或安全的 CI/CD Secret 中；不把密钥写进源码、提交记录或浏览器产物。”

### 3. CI、CD 与 Pipeline

- **CI（Continuous Integration，持续集成）**：代码变更后自动运行检查，例如安装依赖、Lint、类型检查、测试和构建。
- **CD（Continuous Delivery / Deployment，持续交付 / 持续部署）**：将通过验证的版本准备好发布，或自动部署到目标环境。不同团队对 Delivery 与 Deployment 的使用略有区别。
- **Pipeline（流水线）**：把检查、构建、制品保存、部署、健康检查等步骤编排起来。
- **Artifact（构建产物）**：某次构建生成并可被部署、追踪的文件或镜像。
- **Release（发布版本）**：对外提供的一个明确版本，最好能追溯到提交、构建和变更记录。

成熟的交付流程不应该只是“把代码推上去”。更可靠的链路是：

```text
Commit / Pull Request
        ↓
Install from lockfile
        ↓
Lint + Type Check + Test
        ↓
Build Artifact
        ↓
Deploy to Preview / Staging
        ↓
Smoke Test / Health Check
        ↓
Production Release
        ↓
Observe Metrics + Errors
```

### 4. Preview、Staging、Production 与 Feature Flag

- **Preview Deployment（预览部署）**：为分支或 Pull Request 创建临时可访问版本，方便在合并前检查页面。
- **Staging（预发布环境）**：尽量接近生产配置，用于验证部署和集成行为。
- **Production（生产环境）**：真实用户使用的环境。
- **Feature Flag（功能开关）**：把功能是否对用户开放与代码是否已经部署分离。可以先部署代码，再逐步开放功能，但仍需考虑开关默认值和失效时的行为。
- **Smoke Test（冒烟测试）**：发布后快速验证关键路径仍然可用，例如首页加载、登录和主要 API 请求。

“部署成功”只是平台接受了部署，不等于用户路径正常。至少应验证页面能打开、静态资源加载成功、API 地址正确、认证没有失效、关键操作可完成。

### 5. Rollback、Canary、Blue-Green 与 Cache Invalidation

- **Rollback（回滚）**：出现问题时恢复到上一个已知可用版本。前提是旧版本仍可部署，且数据库变更具有兼容性。
- **Canary Release（金丝雀发布）**：先把新版本暴露给一小部分流量或用户，观察指标后再扩大范围。
- **Blue-Green Deployment（蓝绿部署）**：准备两套环境，在验证后切换流量，降低切换风险，但需要额外资源和状态管理。
- **Cache Invalidation（缓存失效 / 清理）**：让 CDN 或浏览器不再使用过期资源。静态文件通常适合使用带内容哈希的文件名与长期缓存策略。
- **Database Migration（数据库迁移）**：变更表结构或数据。它通常比回滚应用代码更棘手，因为旧代码和新结构可能无法兼容。

前端常见故障之一是 HTML 已更新，但浏览器或 CDN 仍缓存旧 JavaScript；另一个是新前端已经发布，却调用了尚未部署或不兼容的 API。发布必须考虑前后端兼容窗口，而不是假设所有组件会同时更新。

### 6. 发布相关表达：把“上线一下”变成可执行任务

| 模糊说法 | 更准确的工程表达 |
|---|---|
| 帮我发布一下 | 说明目标环境、触发方式、构建命令、部署目标和验收路径 |
| 线上打不开 | 区分 DNS / 网络、HTTP 状态码、静态资源、运行时异常和 API 错误 |
| 页面还是旧的 | 检查部署版本、CDN 缓存、浏览器缓存、Service Worker 和资源哈希 |
| 先上去看看 | 创建 Preview Deployment，在预览环境执行关键路径验收 |
| 出问题就回退 | 明确回滚版本、触发条件、负责人、数据兼容性和恢复步骤 |
| 不能影响老用户 | 设计向后兼容的 API、渐进发布、功能开关和回滚方案 |

## 十一、把术语变成一份可执行的 AI 需求

我更倾向于把页面需求拆成七个维度，而不是写一段很长但含糊的自然语言。

| 维度 | 需要说明什么 |
|---|---|
| 目标与用户 | 谁使用页面，要完成什么任务 |
| 页面结构 | 页面区块、组件层次、导航关系 |
| 布局与视觉 | 宽度、列数、间距、对齐、主题 |
| 交互与状态 | 用户动作、状态变化、加载与错误反馈 |
| 数据与接口 | 字段、请求、响应、Mock 或真实 API |
| 工程约束 | 技术栈、现有组件、改动范围、权限 |
| 验收标准 | 什么结果可以被观察、测试和判定为完成 |

### 示例：从模糊描述到工程描述

**模糊版本：**

“帮我做一个用户管理页面，要现代一点，能搜索和编辑。”

**更清晰的版本：**

```text
目标：
为后台管理员实现用户管理页面，支持查找、查看和编辑用户。

页面结构：
- 左侧固定宽度的导航栏，右侧为主内容区。
- 主内容区包含页面标题、筛选表单和用户数据表格。
- 编辑用户时打开右侧 Drawer，不跳转页面。

布局与视觉：
- 桌面端内容区最大宽度 1200px。
- 筛选区使用 Flex 布局，字段间距 16px。
- 表格列为：姓名、邮箱、状态、创建时间、操作。
- 复用项目已有颜色、按钮、输入框和间距规范。

交互：
- 支持按姓名/邮箱搜索，按状态筛选。
- 支持后端分页；修改筛选条件后回到第一页。
- 点击编辑打开 Drawer；取消不保存，确认后提交。
- 提交期间显示 Loading 并防止重复提交。
- 处理成功、空结果、请求失败和字段校验错误。

工程约束：
- 先检查现有路由、组件库、API 封装和权限机制。
- 优先复用已有组件，不引入新的 UI 框架。
- 若 API 尚未提供，先用 Mock Data 并隔离数据访问层。

验收：
- 搜索、筛选、分页、编辑均可实际操作。
- 加载、空数据、错误和成功状态均有明确表现。
- 桌面与窄屏布局可用。
- 运行项目已有的 lint、类型检查和相关测试。
```

这里真正起作用的不是 Prompt 更长，而是它把**目标、约束、状态和验收**分开了。AI 更容易据此做计划，开发者也更容易检查结果。

## 十二、我的进一步思考：术语是一种“压缩歧义”的接口

从软件工程角度看，人与 AI 的协作也需要接口。

自然语言很灵活，但同一句话可能对应许多不同实现。“做一个弹窗”可能指 Modal、Drawer、Popover，甚至独立页面。术语提供了相对稳定的概念边界；示例、尺寸、状态和验收条件则进一步限制解释空间。

可以把它理解为：

```text
模糊目标
   ↓ 术语澄清
结构化需求
   ↓ 工程约束
实现计划
   ↓ 代码生成
可运行结果
   ↓ 测试与人工验收
反馈 / 修正
```

这也解释了为什么只会写 Prompt 不一定能做好 AI 开发。真正有效的协作还需要理解项目上下文、知道术语对应的技术边界，并能判断生成结果是否满足要求。

我认为最值得优先掌握的不是所有前端 API，而是三类知识：

1. **结构词汇**：组件、布局、路由、表单、状态。
2. **行为词汇**：事件、校验、加载、错误、权限、请求。
3. **验证词汇**：响应式、可访问性、类型检查、测试、回归。

它们能覆盖大量日常页面开发，也能帮助后端工程师更准确地描述全栈任务。

## 十三、结语

AI 降低了编写代码的门槛，却没有让需求歧义、系统边界和质量验证自动消失。

前端术语并不是为了显得专业，而是为了把“我想要什么”逐步转换成“系统应该如何表现，以及怎样证明它做对了”。

当我们能够准确说出组件、布局、状态、路由、接口和验收条件时，就不必亲自手写每一行前端代码，也能更可靠地指导 AI 完成开发。

**好的 AI 开发沟通，不是把一句话写得更华丽，而是让每个关键要求都能被实现、观察和验证。**
