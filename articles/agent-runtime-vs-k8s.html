Agent Runtime 与 Kubernetes：相似的外壳，不同的内核

团队容易把 Agent 当 Pod、把工具当 Sidecar。外壳能借，内核不能假装一样。

2026-08-28 chengguruchun Agent Kubernetes Runtime

Kubernetes 成功，是因为它把「期望状态 → 实际状态」变成了可运维的循环。Agent 平台如果只抄 YAML 和调度器外形，却忽略执行语义，会得到一个看起来很云原生、实际上无法问责的系统。

对照表

Comparison · Kernel Differences 维度 │ Kubernetes │ Agent Runtime ──────────────┼─────────────────────────┼────────────────────────── 调度对象 │ 容器副本 / Pod │ 目标驱动的执行会话 成功标准 │ Ready / 健康检查 │ 约束下的任务完成度 状态 │ 无状态或外置存储 │ 记忆、轨迹、工具副作用 失败语义 │ 重启、重调度 │ 改计划、补偿、人工接管 幂等假设 │ 多数控制器可重入 │ 工具副作用常常不可重入 确定性 │ 期望高 │ 模型输出本质非确定

可迁移的部分

  • 声明式期望：把「允许做什么」写成数据，而不是藏在对话里。
  • 控制器循环：持续调和：预算、策略、进度、风险。
  • 可观测标准：统一日志、指标、追踪——对 Agent 还要加轨迹与成本。
  • 隔离：命名空间、配额、网络策略的思想，映射到工具与数据平面。

危险的迁移

假设执行可幂等；假设输出可字节级复现；假设「重启 Pod」能修好错误的外部写入。Agent Runtime 需要效应管理：哪些调用可重试、哪些必须 saga 补偿、哪些必须停下来等人。

设计启发式

先问：这次失败重放是否安全？如果答案是否，就不要用 K8s 的重启心智去覆盖它。

Desired State 还是 Desired Policy？

开放世界任务很难收敛到单一终态。更稳的抽象或许是：在策略与预算边界内最大化进展，并显式保留「不确定区间」。这时控制面管的是政策与风险，而不是副本数。

开放问题

  • Goal 对象的 API 应该长成什么样？能否像 CRD 一样演进？
  • 工具会话（Tool Session）是否需要独立生命周期，像 ephemeral container？
  • 多集群/多模型路由，是否会重演 federation 的复杂性？
