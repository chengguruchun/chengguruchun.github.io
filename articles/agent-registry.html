Agent Registry：能力发现、版本契约与信任边界

当 Agent 开始互相调用，硬编码终点会迅速腐烂。注册中心必须升级为能力目录。

2026-09-02 chengguruchun Agent Registry 契约

服务发现解决「谁在哪里」。Agent Registry 还要解决「谁能做什么、以什么契约、被谁信任」。它是名字服务 × 模型目录 × 安全策略的交叉点。

最小数据模型

Identityagent id、所有者、环境、区域
Capabilities输入输出 schema、工具集、模态
Contract版本、兼容策略、弃用窗口
Trust可见性、调用权限、签名/认证
Hints延迟、成本、成功率、限额
Flow · Discovery to Invoke Caller Agent │ query(capability, constraints) ▼ Registry ──▶ candidates + contracts + trust decision │ ▼ Policy check (caller ∩ callee ∩ data class) │ ▼ Invoke via Tool/Agent Gateway ──▶ Audit log

契约比 endpoint 更重要

静默改变工具参数或输出结构，会让上游 Agent 的计划器在「看起来成功」的情况下做错事。Registry 应支持：版本并行、兼容矩阵、以及用可执行示例/契约测试作为回归闸门。

信任边界

不是所有可发现的 Agent 都可以调用。企业内部还要区分：只读分析 Agent、可写业务 Agent、可触达资金/库存的高危 Agent。发现与授权必须拆开——和微服务的「DNS ≠ IAM」同一道理。

开放问题

  • 能力描述用自然语言、JSON Schema，还是「测试即契约」？
  • 跨组织 Registry 是否需要像包管理一样的签名与供应链审计？
  • 运行时提示（成本/成功率）如何避免变成被刷的广告牌？
