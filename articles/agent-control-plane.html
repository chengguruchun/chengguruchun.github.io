Agent Control Plane：把智能体当成可治理的运行时

多数 Agent 应用停在提示词与工具调用。进入生产后，缺少的不是更聪明的模型，而是控制面。

2026-08-20 chengguruchun Hangzhou Agent Control Plane 分布式系统

后端与分布式训练给我的第一反应很直接：任何会在生产里长时间运行、会调用外部世界、会产生副作用的东西，都不能只靠「一次推理」。它需要准入、编排、策略、观测、终止。对微服务，我们叫它控制面；对 Agent，名字可以换，结构不能省。

1. 问题定义：聊天机器人不是工作负载

演示里的 Agent 像对话。生产里的 Agent 更像带目标的工作负载：它有预算（token / 钱 / 时间），有工具权限，有可能陷入循环，有可能对外部系统造成不可逆写入。如果团队只优化提示词，系统债会堆在运行时之外——直到某次工具调用打穿了库存或票据。

判断标准

如果一个 Agent 不能被安全地暂停、审计、限流与回放，它就不该碰生产副作用。

2. 控制面五件套

意图准入目标合法性、租户、预算、数据分级
执行编排单/多 Agent、同步异步、队列化
策略护栏工具白名单、人机回环、写入闸门
观测审计轨迹、成本、失败分类、证据链
生命周期挂起、恢复、终止、重放、归档

这五件套不是「平台团队的附加功能」，而是 Agent 作为运行时的最小完备集。缺观测，你无法改进；缺终止，你无法止损；缺准入，你无法多租户。

3. 与服务控制面的同构与异质

同构：都需要声明期望、调节实际、暴露信号。控制器循环（reconcile）仍然好用——只不过「期望」不再是副本数，而是「在约束下推进目标」。

异质：Agent 的成功不是 Ready 探针为真，而是约束满足与任务完成度；失败也不是简单重启能治愈——可能需要改计划、换工具、升级给人。

4. 工程落地的最小路径

  1. 先做 Tool Gateway：所有副作用走网关，带鉴权、配额、审计。
  2. 再做 Run Record：每次执行有不可篡改的轨迹与成本账本。
  3. 然后做 Policy-as-data：谁能用哪些工具，写在数据里，而不是散落在提示词。
  4. 最后才考虑复杂多 Agent 编排——否则是在放大失控面。

5. 开放问题

  • 控制面该嵌入模型运行时，还是像服务网格一样旁路？
  • 策略语言要多强？DSL、Rego，还是「可执行测试即策略」？
  • 跨厂商模型时，统一的 Run Record schema 如何演进而不碎？
