# 从 Agent 拓扑到任务协作：重新设计 Multi-Agent Runtime

## 一个常见的分类误区：它们不在同一个维度

讨论 Multi-Agent 架构时，经常会看到几种并列分类：全分布式 Swarm、中心化 Orchestrator、Gossip 式传播。它们看起来像三种互斥架构，但实际上混合了不同层次的概念。

Orchestrator 描述的是**协调权放在哪里**；Swarm 通常描述一种更自治、弱中心的协作形态；Gossip 描述的则是**信息如何在节点之间传播**。一个系统可以采用星型拓扑、由 Orchestrator 调度，同时用事件广播通知状态变化；也可以采用 Mesh 拓扑，但仍通过某个服务对任务结果进行仲裁。

如果把它们当成同一维度的选项，就容易在架构讨论中陷入“中心化还是分布式”的二元争论，而忽略真正影响系统行为的设计选择。

本文的核心判断是：

> **企业级 Multi-Agent Runtime 应以 Task 与 Shared State 为组织中心：Agent 是可替换的执行单元；拓扑、通信、协调和治理应作为正交维度设计；最终结果由独立验证形成质量闭环。**

这是一项架构主张，而不是已经被普遍证明的定律。它适合需要长任务、审计、恢复、权限控制和稳定交付的系统；开放式研究、创意探索或低风险协作，可能更适合提高 Agent 自治程度。

## 一、把 Multi-Agent 拆成四个正交维度

设计多 Agent 系统时，我建议先回答四个问题，而不是先选择某个框架。

### 1. 拓扑：谁和谁连接？

拓扑描述 Agent、协调者和共享资源之间的连接关系。

| 拓扑 | 结构 | 典型特点 |
| --- | --- | --- |
| 星型 Star | 一个中心连接多个 Worker | 控制集中、易审计，中心可能成为瓶颈 |
| 树型 Hierarchical | 多层 Supervisor / Team | 适合大规模分组，跨层协作成本较高 |
| 黑板 Blackboard | 多个 Agent 围绕共享工作区协作 | 降低直接耦合，需要解决并发与状态冲突 |
| Mesh | Agent 之间存在多条直接连接 | 自治和弹性较高，通信与治理复杂 |

星型结构适合由一个 Orchestrator 负责计划、分配、重试和验收的任务。树型结构则允许子团队在局部范围内自主安排工作，例如全局 Manager 管理项目，Backend Lead 和 Frontend Lead 分别管理自己的任务组。

黑板架构值得特别关注：Agent 不一定需要知道其他 Agent 的内部实现，只要理解共享工作区的数据协议，就可以读取任务、提交产物或报告问题。黑板可以是数据库中的任务状态、版本化文档、对象存储中的产物索引，或它们的组合。

Mesh 则允许 Agent 更自由地发现和调用彼此，但连接数会快速增长。若 N 个节点完全互连，潜在的无向连接数为：

[
E = \frac{N(N-1)}{2}
]

这意味着增加 Agent 不只是增加算力，也会扩大通信、冲突和权限治理的空间。

### 2. 通信：信息如何流动？

通信机制描述消息的传递方式，不等于拓扑。

- **点对点 handoff：** 一个 Agent 将明确的任务或控制权交给另一个 Agent。
- **广播 / fan-out：** 一个事件被发送给多个订阅者。
- **Gossip：** 节点选择部分邻居传播信息，经过多轮扩散。
- **共享状态读写：** Agent 通过数据库、黑板或对象存储交换工作结果。
- **事件总线：** 发布者发出领域事件，订阅者按需响应。

Gossip 尤其容易被误解。它解决的是分布式环境中的信息传播问题，不负责决定任务由谁执行，也不保证节点对事实形成一致判断。

例如，Tester 发现集成测试失败，可以把事件写入任务状态并发布通知。订阅该事件的 Coder、Team Orchestrator 或 Critic 都可以被唤醒。若采用 Gossip，信息可以在节点间逐步扩散；但“大家都知道失败了”并不等于“系统已经确定由谁修复”。

因此，通信协议要与任务协调机制分开设计。

### 3. 协调：谁决定下一步做什么？

协调机制决定任务分配、执行顺序、冲突处理和结果采纳。

| 机制 | 决策方式 | 适用场景 |
| --- | --- | --- |
| 中心调度 | Orchestrator 规划并分配 | 有明确交付目标的企业任务 |
| 任务认领 | Agent 从任务池原子领取任务 | 可并行的 Worker 执行 |
| 投票 | 多个 Agent 对候选方案表态 | 多视角评审、方案比较 |
| 规则仲裁 | 根据约束、证据和策略决定 | 权限、预算、合规和验收 |
| 竞价 / 匹配 | Agent 根据能力、负载和成本竞争任务 | 动态资源分配 |

任务认领看起来是一个简单模式，实际需要租约、心跳、超时回收、幂等执行和重复投递处理。多个 Agent 同时看到一个待处理任务时，必须有原子机制保证只有一个有效认领者，或者允许重复执行但保证结果提交幂等。

投票也不等于真理。三个使用相同模型、相同上下文的 Agent 可能犯同一种错误。投票适合表达多视角意见，最终采纳仍应检查证据、独立性和业务约束。

还要区分应用层投票与分布式共识协议。Raft、Paxos 解决的是节点故障和网络不确定条件下的状态复制与一致性问题；让几个 LLM Agent 用自然语言讨论并投票，通常不能称为 Raft 式共识。

### 4. 治理：谁拥有执行和决策权限？

治理回答的是：谁可以创建任务、调用工具、修改共享状态、批准高风险动作，以及终止或回滚执行。

它与拓扑无关。全 Mesh 系统可以有严格的中心化权限策略；星型系统也可以允许 Worker 在限定范围内自主决策。

企业场景通常需要将以下权限分开：

- **计划权：** 谁能创建、拆分和重排任务。
- **执行权：** 谁能调用工具、访问资源和修改文件。
- **提交权：** 谁能将产物写入共享状态或合并代码。
- **批准权：** 谁能批准资金、外部消息、生产变更等高风险操作。
- **终止权：** 谁能取消任务、撤销租约或触发回滚。

把这四个维度分开，才能组合出真正清晰的架构，而不是只给系统贴上 Swarm 或 Orchestrator 的标签。

## 二、几种典型架构如何组合？

以下是常见组合，而不是互斥的产品分类。

### 星型 + handoff + 中心仲裁

这是企业任务编排的常见起点。Orchestrator 维护任务图，Worker 负责执行，结果返回中心节点，由中心决定继续、重试或验收。

优势是可控、可追踪；缺点是中心节点可能成为吞吐瓶颈和复杂度集中点。

### 树型 + 局部自治 + 分层仲裁

全局协调者负责目标和资源，Team Orchestrator 负责局部计划，子 Agent 执行具体任务。团队内部可以使用点对点消息和共享状态，跨团队则通过稳定契约协作。

它适合任务规模较大、领域边界相对清晰的系统，但要防止每一层都重复规划、总结和转发上下文。

### 黑板 + 事件唤醒 + 工具验证

Agent 读取共享工作区，根据状态领取工作，完成后提交产物与验证证据。事件机制负责唤醒相关参与者，规则或验证器决定状态是否可以推进。

它降低了 Agent 之间的直接依赖，但黑板需要版本控制、并发写入策略、权限隔离和状态迁移约束。

### Mesh + Gossip + 分布式协商

Agent 自主发现伙伴、交换信息并形成候选方案。它适合开放式研究、多视角探索和动态协作，但需要额外处理消息风暴、重复传播、循环讨论、冲突结果和最终责任归属。

对高风险生产任务而言，通常仍需要一个明确的验收与治理边界。

## 三、为什么生产系统常采用“控制面中心化，执行面分布式”？

全分布式并不天然优于中心化。生产系统还要面对成本、延迟、可观测性、安全和恢复等约束。

LLM Agent 与传统分布式 Worker 有一个重要差异：Agent 的每次推理都可能产生不同的行动决策。多一次 Agent 交互，可能意味着多一次模型调用、更多上下文、更多 Token 和新的不确定性。

因此，生产系统常见的折中是：

**控制面中心化，执行面分布式，局部协作自治，结果独立验证。**

控制面负责：

- 任务创建、规划和生命周期管理；
- Agent 选择、资源配额与预算控制；
- 权限、审批和安全策略；
- Checkpoint、超时、取消与恢复；
- 运行轨迹、成本和最终验收。

执行面负责：

- Agent 的推理循环；
- 工具调用和产物生成；
- 局部任务协作；
- 进度、日志和结果回报。

这与 Kubernetes 的 Control Plane / Worker 思想有相似之处，但不能简单等同。Kubernetes 调度的是具有明确容器和资源语义的工作负载；Agent Runtime 还要管理模型推理、上下文构造、工具权限、非确定性行动和结果验证。

中心化也不意味着每条消息都必须经过 Global Orchestrator。局部 Team 可以直接协作，只有涉及任务状态迁移、跨团队依赖、预算或权限边界时，才需要上层协调。

## 四、为什么要以 Task 和 Shared State 为中心？

这是本文最核心的架构判断。

如果以 Agent 为中心组织系统，通常会出现这样的交互：

```text
Agent A → Agent B → Agent C → Agent A
```

每个 Agent 都需要理解其他 Agent 的角色、上下文和调用协议。随着参与者增多，协作关系和状态容易散落在对话历史中。

如果以 Task 为中心，结构会变成：

```text
                 Task
                  |
       +----------+----------+
       |          |          |
     Plan       State      Artifacts
       |          |          |
     Agent A    Events    Agent B
                  |
               Evidence
```

Task 是持久化的业务对象，Agent 是处理它的执行者。Agent 可以被替换、扩容、重试，甚至切换模型；但任务目标、依赖、产物、状态和验收证据必须持续存在。

一个任务至少需要表达：

| 字段 | 含义 |
| --- | --- |
| task_id | 稳定任务标识 |
| goal / spec | 目标、约束和验收标准 |
| status | 当前生命周期状态 |
| dependencies | 前置任务和依赖关系 |
| assignee / lease | 当前执行者和租约 |
| artifacts | 代码、文档、文件等产物引用 |
| events | 状态变化和执行事件 |
| evidence | 测试、检查和外部确认结果 |
| checkpoint | 可恢复的执行位置 |
| budget | Token、时间和工具调用预算 |

这并不要求所有内容都放进一张数据库表。结构化状态可以放在关系数据库中，事件可以进入消息系统，大型产物放在对象存储，运行轨迹进入日志或追踪系统。关键是存在稳定的 Task ID 和可追溯的关联关系。

### Task、Shared State、Memory 与 Context 不是同一个东西

这四个概念需要明确区分：

- **Task：** 当前要完成什么，约束和验收条件是什么。
- **Shared State：** 当前任务执行到哪里，已经产生什么结果。
- **Memory：** 系统或 Agent 从过去保留了哪些可复用信息。
- **Context：** 当前这次推理实际提供给 Agent 的信息集合。

例如，项目使用 Spring Boot 属于可复用的项目记忆；“数据库设计已完成，等待 API 实现”属于当前任务状态；Coder 当前看到的 API 契约、相关代码和任务说明才是它这轮推理的 Context。

把它们混在一起，会导致共享状态被当作长期记忆、过期信息被注入上下文，或任务进度只存在于某个 Agent 的对话里。

## 五、黑板与消息总线如何协作？

共享状态和消息传递不是二选一。

黑板负责保存**事实和当前状态**，消息总线负责传递**状态变化的通知**。

例如 Tester 完成测试后：

1. 将测试报告写入对象存储。
2. 在 Task 中追加 artifact 引用和 evidence。
3. 通过事务或 Outbox 发布 `TestCompleted` 事件。
4. 订阅者收到事件后读取最新 Task 状态。
5. Orchestrator 或规则引擎判断是否进入下一阶段。

消息可以重复投递，消费者也可能延迟处理，因此不能把“收到事件”当作唯一事实来源。消费者应使用事件 ID 去重，并重新读取任务的权威状态。

并发更新也需要显式处理。可以使用乐观锁版本号、状态迁移条件、任务租约和幂等提交。例如，只有任务仍处于 `in_progress` 且版本号匹配时，某个 Agent 才能提交结果；过期租约的执行者不能覆盖新执行者的结果。

这样，黑板提供状态事实，消息总线提供传播效率，Runtime 提供状态迁移规则。

## 六、一个企业级 Multi-Agent Runtime 的参考结构

可以将系统划分为四层：

```text
┌────────────────────────────────────────────┐
│ Control Plane                               │
│ Planner · Scheduler · Policy · Lifecycle   │
│ Budget · Approval · Evaluation              │
└──────────────────────┬─────────────────────┘
                       │ Task / Command
┌──────────────────────▼─────────────────────┐
│ Team / Agent Runtime                        │
│ Backend Team       Frontend Team            │
│ Team Lead          Team Lead                 │
│ Coder / Tester     Designer / Coder          │
│ Local handoff      Local collaboration       │
└──────────────────────┬─────────────────────┘
                       │ Read / Write / Events
┌──────────────────────▼─────────────────────┐
│ Shared Work Plane                           │
│ Task State · Artifacts · Events · Evidence  │
│ Checkpoints · Contracts · Version           │
└──────────────────────┬─────────────────────┘
                       │
┌──────────────────────▼─────────────────────┐
│ Infrastructure                              │
│ Message Broker · DB · Object Store           │
│ Tool Gateway · Sandbox · Tracing             │
└────────────────────────────────────────────┘
```

建议把核心模块定义为：

| 模块 | 主要职责 |
| --- | --- |
| Agent Registry | 登记 Agent 能力、版本、模型和可用状态 |
| Planner | 目标分析、任务拆解、依赖图生成 |
| Scheduler | 选择执行者、并发控制、租约和资源分配 |
| Runtime | 执行推理循环、工具调用和局部协作 |
| Message Bus | 事件通知、任务唤醒和异步通信 |
| Shared State | Task 状态、产物索引、版本和证据 |
| Memory | 可复用的经验、事实和知识 |
| Tool Gateway | 工具发现、路由、权限和审计 |
| Checkpoint | 保存恢复所需的执行状态 |
| Evaluator | 独立验证结果、判断是否满足验收条件 |
| Observability | 轨迹、Token、延迟、错误和成本 |

Agent Registry 不应只是一个名字列表。能力描述最好包含输入输出 Schema、适用任务类型、权限范围、模型要求、成本估计和验证方式。Scheduler 才能结合任务需求与 Agent 能力进行匹配，而不是只根据 Agent 名称做硬编码路由。

## 七、任务生命周期：让失败成为可管理的状态

企业级 Runtime 不应该把一次 Agent 对话当作完整的任务生命周期。可以为 Task 定义显式状态机：

```text
Created
   ↓
Planned
   ↓
Ready → Claimed → Running
                   ↓
             Verifying
              /      \
          Accepted  Rejected
                       |
                    Replanned
                       |
                     Ready

Running → WaitingApproval
Running → Failed / Cancelled
```

状态迁移需要定义合法条件，而不是让 Agent 任意写入字符串。

例如：

- `Ready → Claimed`：必须成功获得任务租约。
- `Claimed → Running`：执行者身份、权限和预算检查通过。
- `Running → Verifying`：必须提交产物引用和执行摘要。
- `Verifying → Accepted`：独立验证满足验收条件。
- `Verifying → Rejected`：记录失败证据，并决定返工还是重新规划。
- `WaitingApproval → Running`：收到有效审批结果。

Checkpoint 也不等于完整保存所有对话。更可靠的恢复方式，是保存任务状态、已提交产物、工具调用记录、外部副作用标识和必要的上下文引用；恢复时根据这些事实重新构造 Context。

对于外部副作用，例如发送邮件、创建工单、扣费或发布部署，必须使用幂等键、审批记录和可追踪的执行结果。单纯重放模型对话，可能重复执行真实世界中的动作。

## 八、验证与治理：谁说任务完成了？

Agent 自己报告成功，不应成为唯一验收依据。

一个更可靠的闭环是：

```text
Agent Execution
      ↓
Artifact Submission
      ↓
Deterministic Checks
      ↓
Independent Evaluator
      ↓
Policy / Human Approval
      ↓
Accepted or Replanned
```

不同任务应采用不同的证据：

- 代码任务：单元测试、集成测试、静态分析、构建结果。
- 数据任务：Schema 校验、数据质量规则、抽样核对。
- 研究任务：来源、证据链、反例和不确定性说明。
- 外部操作：工具返回结果、业务系统状态和审批记录。

Evaluator 也不一定是另一个 LLM。能用确定性工具验证的事情，优先使用确定性工具；LLM 更适合处理语义性判断，但应要求引用证据并标明不确定性。

治理策略则要根据风险分级。低风险、可逆的内部操作可以自动执行；涉及生产发布、资金、外部沟通或敏感数据的操作，应要求更严格的审批和审计。

## 九、如何选择架构，而不是追求某种“最先进”的拓扑？

可以从任务特征出发：

| 任务特征 | 更合适的起点 |
| --- | --- |
| 目标明确、步骤可规划、需要审计 | 星型 Orchestrator |
| 任务规模大、团队边界清楚 | 树型分层协调 |
| 多角色围绕同一产物迭代 | 黑板 + 事件通知 |
| 开放式探索、动态发现协作者 | 局部 Mesh / Gossip |
| 大量独立、可重试的子任务 | 任务池 + 原子认领 |
| 高风险、需要强约束的操作 | 规则仲裁 + 人工审批 |

这些模式可以混合。真正重要的是明确哪些行为允许自治，哪些状态必须持久化，哪些操作必须经过治理，以及最终结果如何被验证。

## 十、如何验证 Task-centric Runtime 是否真的更好？

“以 Task 为中心”是架构主张，需要通过实验与其他组织方式比较，而不能只凭设计直觉。

可以设计一个对照实验：使用同一组需求、模型、工具和预算，分别采用 Agent-centric 对话编排与 Task-centric 状态编排，记录：

1. 任务完成率和验收通过率；
2. 从开始到交付的端到端耗时；
3. 重复工作量、上下文重复传递和无效模型调用；
4. 并发冲突、任务认领失败和状态覆盖次数；
5. 失败恢复成功率与恢复耗时；
6. 每个验收通过任务的总 Token 和工具成本；
7. 人工介入次数与高风险操作拦截率。

实验还要区分任务类型。短对话、创意探索和低风险任务，可能并不需要完整的持久化 Task Runtime；长周期、多步骤、跨系统和可恢复任务则更可能受益。

如果 Task-centric 设计只增加了状态管理和工程成本，却没有改善可恢复性、审计性或交付质量，就应该重新评估其适用范围。

## 结语：Agent 是执行单元，Task 才是长期存在的协作对象

Multi-Agent 架构不应该停留在“多个 Agent 如何互相调用”的层面。拓扑决定连接方式，通信决定信息流动，协调决定任务如何推进，治理决定哪些行为被允许。它们是可以组合的设计维度。

对企业级 Runtime，我更倾向于以 Task 和 Shared State 作为系统的持久化组织中心：Task 保存目标、依赖和生命周期，Shared State 保存执行事实、产物和证据，Agent 根据能力被调度来处理任务，独立验证器判断结果是否满足要求。

这样，Agent 可以替换，模型可以升级，执行节点可以扩缩容，协作拓扑也可以调整；只要 Task 的身份、状态、契约和证据保持稳定，系统就不必依赖某个 Agent 的对话历史来维持整个任务。

**最终要构建的不是一个 Agent 互相聊天的网络，而是一套能够组织任务、共享事实、控制行动、验证结果并从失败中恢复的 Runtime。**
