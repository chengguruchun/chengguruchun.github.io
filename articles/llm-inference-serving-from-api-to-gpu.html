从 API 请求到 GPU 执行：拆解大模型推理服务架构

从云端接入、API Gateway、模型路由，到 vLLM/SGLang 的请求队列、连续批处理、KV Cache 管理，再到 Tensor Parallel、CUDA、NCCL 与 GPU 执行，串起一次流式推理请求的完整链路。

思路 2026-10-30发表 2026-10-30作者 chengguruchun

理解大模型推理，不能只盯着模型本身。一次 Chat Completions 请求从客户端发出，到最终逐个 Token 返回，中间经过一套分层的在线服务系统：网络接入、API 服务、模型路由、推理运行时、GPU 并行计算，以及反向的流式响应。

本文以一次请求一个模型的流式生成请求为主线，拆开这些层次，并重点解释 vLLM / SGLang、KV Cache、Continuous Batching、Tensor Parallelism 与 CUDA 各自负责什么。

一、完整请求链路

Client → DNS / GSLB → Regional LB / WAF → API Gateway
  → Model Router → vLLM / SGLang Runtime
  → Scheduler / Continuous Batching / KV Cache
  → GPU Workers（TP / PP / NCCL / CUDA）
  → SSE Token Stream → Client

这是逻辑架构图，不意味着每家云厂商都部署完全相同的组件。小规模部署可能没有独立 Model Router；大型平台则可能把接入、模型控制面和 GPU 数据面拆开。CDN 在动态模型 API 场景通常偏向边缘接入、防护和网络加速，不应简单理解为缓存生成结果。

二、入口层：DNS、负载均衡与 API Gateway

客户端首先通过 DNS 解析服务域名。GSLB 可结合地域、网络质量、可用区健康状态和容量选择区域；区域 LB 把连接分发到健康的 API 实例。API Gateway 处理身份认证、API Key、租户配额、限流、请求校验、审计和用量元数据。

流式 SSE 请求还要求代理正确处理长连接、超时、断连和背压。入口层管理的是请求和访问策略，不直接负责 GPU 上的 Token 计算。

三、Model Router：选择模型部署和实例

请求中的 model 字段先映射到模型或版本，再映射到具体部署副本。例如 deepseek-v3 可以对应一个部署，而该部署又有多个 serving replicas；每个 replica 可能由一组 GPU worker 组成。

路由器综合考虑实例健康、排队长度、运行请求数、显存压力和延迟目标。多轮对话还可能考虑会话亲和性、Prefix Cache / KV Cache 局部性：缓存仍在且实例未过载时，复用已有前缀可以减少重复计算。但缓存可能被驱逐，故障或负载也会改变选择，缓存亲和性不是绝对规则。

四、vLLM / SGLang：推理运行时

推理运行时维护请求状态、等待队列、调度、批处理、KV Cache 生命周期，并调用模型执行代码。等待队列通常由运行时在 CPU 侧维护，不是 GPU 自己管理用户请求队列；平台外层也可能有独立队列，两者职责不同。

Continuous Batching：动态批处理

Batch 就是批量处理。连续批处理会在请求不断到达和完成时动态调整执行批次。假设 A、B、C 正在生成，B 已结束，运行时不必等 A、C 全部结束才处理下一批；它可以在调度边界移除 B，并让等待中的 D 进入后续执行批次。这减少 GPU 空转、提升总体吞吐，但吞吐提升不等于单请求延迟必然下降。

Prefill 与 Decode

Prefill 处理输入 Prompt，计算输入 Token 并建立 KV Cache，通常更偏计算密集。Decode 则基于已有上下文逐步生成 Token，每步需要读取历史 KV Cache，常更容易受显存带宽影响。请求长度、生成进度和缓存占用不断变化，使调度远比普通线程池复杂。

五、KV Cache：重要的显存资源

Transformer 生成时会重复使用历史 Token 的 Key / Value。缓存这些张量可避免每步重新计算完整历史，但会占用 GPU 显存，并随上下文长度和并发请求增长。

KV Cache ≈ 2 × 层数 × Token 数 × KV Heads
           × Head Dimension × 每元素字节数

实际占用还受模型结构、张量并行切分、缓存精度和内存对齐影响。vLLM 的 PagedAttention 将 KV Cache 切成固定大小 Block 管理，减少连续大块分配的碎片和浪费。SGLang 的 RadixAttention / Radix Cache 则支持共享前缀的缓存复用。缓存管理影响并发容量和调度，不只是节省一点显存。

六、SGLang 与 CUDA：运行时和计算平台

SGLang / vLLM 管理请求、调度、批处理、缓存和模型执行流程；CUDA 提供 NVIDIA GPU 编程与执行平台；GPU 是实际执行矩阵运算和注意力计算的硬件。运行时会通过 PyTorch、Triton 或自定义 CUDA Kernel 组织计算，最终由 GPU 执行算子。

可以类比数据库 Server 层与底层执行能力的分工，但类比有边界：SQL 执行计划相对明确，而 LLM Decode 是逐 Token 持续推进，KV Cache 也会动态增长。

七、一个模型如何使用多张 GPU

Tensor Parallelism（TP）把模型层中的权重矩阵或计算维度切分到多张 GPU。TP=8 表示相关计算由 8 张 GPU 分担，并在需要时交换或归约局部结果。

Pipeline Parallelism（PP）则把模型不同层放在不同 GPU 或 GPU 组上，输入依次经过各阶段。TP 是切分同一层的计算，PP 是分布不同层。

  • NCCL：提供 All-Reduce、All-Gather、Reduce-Scatter 等集合通信。
  • NVLink / NVSwitch：服务器内部 GPU 高速互联。
  • InfiniBand / RoCE：服务器之间高速网络，常与 RDMA 配合。

TP=8 并非简单地把模型平均切八份。切分方式、通信拓扑、算子实现和调度都要协同设计；通信开销过高时，增加 GPU 数量未必线性提升性能。

八、职责边界总结

层次核心问题组件
接入流量进入哪个区域DNS、GSLB、WAF、LB
API 服务谁能调用、额度多少Gateway、Auth、Rate Limit
模型路由选择哪个部署副本Model Router
推理运行时哪些请求当前执行、如何复用缓存vLLM、SGLang、Scheduler
分布式执行模型如何跨卡协作TP、PP、NCCL
底层计算算子在哪里执行CUDA、GPU Kernel
  1. Model Router 与 Runtime Scheduler 是两层调度：前者选择模型服务实例，后者安排实例内部的执行批次。
  2. Continuous Batching 与 Tensor Parallelism 解决不同问题：前者让多个请求共享算力，后者让一个模型跨多张 GPU 协作。
  3. KV Cache 是运行时管理的关键资源，影响并发容量、缓存复用和请求调度。
  4. SGLang / vLLM 不等于 CUDA：运行时组织请求和计算，CUDA 软件栈提供底层 GPU 执行能力。

结语

大模型推理服务不是“把模型放到 GPU 上，再暴露一个 HTTP 接口”这么简单。它既是在线请求服务系统，也是 GPU 资源调度系统，还是一套围绕 KV Cache 和持续 Token 生成设计的执行运行时。

理解它最有效的方式，是明确每层管理的对象：网络层管理流量，API 层管理调用者，路由层管理模型部署，推理运行时管理请求与缓存，分布式执行层管理 GPU 协作，CUDA 和 GPU 完成底层计算。
